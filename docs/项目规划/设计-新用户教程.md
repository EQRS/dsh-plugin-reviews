# 设计 · 新用户教程（普通用户与访客）

> 状态：设计已定，**尚未撰写正文**
> 目标读者：**访客**与**普通用户**（含投稿者）
> 决策日期：2026-11-08

---

## 1. 为什么要做

站点目前**没有任何教程或引导**。新用户第一次打开会面对六个并列的主导航（插件 / 整合包 / 评测 / 精选 / 讨论区 / 规范），
而这三类内容之间的关系、哪些功能需要登录、投稿从哪进——全都靠猜。

这个问题的成本是隐性的但持续：访客不知道登录能得到什么，就不登录；
注册了的人不知道能投稿，就只是读者。**教程要解决的是「第二次访问还不来」这件事。**

## 2. 范围

**做**

- 访客与普通用户的全部可见功能
- 投稿能力：发评测、提交插件、创建整合包、讨论区发帖
- 「想成为测评员 / 开发者」的**入口指引**（只指路，不写申请流程）
- 三条反馈通道的区别（举报 / 纠错 / 问题反馈）——这是新用户最容易用错的地方

**不做**

- 测评员、开发者、官方测评员等**特殊身份的操作教程**（使用者明确先不做）
- 管理员后台的任何操作
- 付费加速与悬赏（设计已定但未上线）

## 3. 交付形态

使用者裁定「两者都要」，所以：

| 形态 | 路径 | 职责 |
|---|---|---|
| **文档** | `docs/教程-普通用户与访客.md` | 完整版，可离线阅读、可随仓库演进 |
| **站内页** | `/guide` | 从文档裁出的阅读版，登录/未登录都能看 |

**为什么要两份而不是只做站内页**：文档适合完整叙述与搜索，站内页适合「点进去 3 分钟看懂」。
两者内容同源，**以文档为准**，站内页是它的精选版；改内容先改文档再同步站内页。

> 站内页在导航里放哪：**页脚**，不进主导航。主导航已经有六项，再加一项会把原本并排的入口挤乱；
> 而教程属于「第一次用才需要、之后不再看」的内容，放页脚更合适。

## 4. 内容结构

按「读者此刻想干什么」组织，而不是按功能树罗列。

### 4.1 文档版（12 节）

| # | 章节 | 要回答的问题 |
|---|---|---|
| 1 | 这是什么站 | 一句话说清三类内容的关系 |
| 2 | 不登录能做什么 | 访客能看的全部内容 |
| 3 | 登录与它带来的变化 | 凭什么要登录；一张前后对照表 |
| 4 | 找插件 | 目录、筛选、搜索、详情页各块是什么意思 |
| 5 | 读评测 | 结论怎么读、测评档位是什么、投票怎么用 |
| 6 | 整合包 | 和插件的区别、安装命令怎么用 |
| 7 | 精选专栏 | 它和普通评测的位置关系 |
| 8 | 讨论区 | 主干：分区、发帖、两层回复、草稿、举报 |
| 9 | 收藏与个人中心 | 三类收藏、通知、设置 |
| 10 | 我想投稿 | 发评测 / 提交插件 / 创建整合包 / 发帖，四条路各怎么做 |
| 11 | 遇到问题该找谁 | **三条通道怎么选**（重点） |
| 12 | 常见问题 | 10–15 条真实会问到的 |

### 4.2 站内页（6 块）

文档的浓缩版，只保留「第一次用必须知道」：

1. 三类内容分别是什么
2. 要不要登录（前后对照）
3. 怎么找东西（插件 / 评测 / 整合包）
4. 怎么投稿
5. 怎么反馈
6. 常见问题 Top 5

## 5. 每个功能点写到什么颗粒度

使用者裁定「讨论区写主干」，其余章节按同一原则：**写「怎么用」，不写「内部怎么实现」**。

| 该写 | 不该写 |
|---|---|
| 这个按钮在哪、点了会怎样 | 它对应哪张表、哪个接口 |
| 什么情况下会失败、失败后怎么办 | 频控的具体阈值与实现 |
| 哪些内容需要审核、大概多久 | 审核规则的关键词清单 |
| 三类收藏各自独立、夹只能装同类 | 部分唯一索引与 target_kind |

### 5.1 各章颗粒度

| 章节 | 写到哪 |
|---|---|
| 插件目录 | 说明筛选维度与搜索范围即可，不列每个筛选项的取值 |
| 评测详情 | 要讲清**结论档位**与**证据链**这两块，它们是本站区别于普通博客的地方 |
| 讨论区 | 只写：分区是什么、怎么发帖、两层回复（回复的回复不能再往下）、草稿在哪里、怎么举报；**不写**分区申请流程与后台审核 |
| 收藏 | 讲清三类夹互相独立、删夹会把收藏移回默认夹（这是容易误解的行为） |
| 投稿 | 每条路写「从哪个入口进 → 要准备什么 → 提交后会发生什么」 |

## 6. 第 11 节：三条通道怎么选（本教程的重点）

站点有三条容易混淆的反馈通道，**新用户最常在这里用错**。已核实它们的分工：

| 通道 | 入口在哪 | 管什么 | 不管什么 |
|---|---|---|---|
| **举报** | 评测 / 评论 / 帖子 / 回复 / 整合包版本上的「举报」按钮 | 违规内容：垃圾广告、辱骂、错误信息、版权、其他 | **不处理**资料写错 |
| **反馈资料错误** | 插件详情页 | 只改两项：**展示名**、**简介** | 不改分类、不改评测内容 |
| **问题反馈** | 顶部/页脚入口，需登录 | 站点本身的问题：功能异常、账号问题、建议 | 不处理具体某篇内容的对错 |

**为什么把这条单独列一节**：三者的入口位置、处理周期、结果通知方式都不同，
用错通道的后果是「等了很久没人理」。教程里要用一张对照表把它讲死。

## 7. 写作原则

### 7.1 先讲「你能做什么」，再讲「怎么点」

新用户的问题不是「这个按钮在哪」，而是「我来这儿能干什么」。
每章开头用一句话说明这一章能帮他达成什么，再进入步骤。

### 7.2 涉及登录的地方必须标注

全篇统一用两种标记：

| 标记 | 含义 |
|---|---|
| 🔓 | 不登录也能用 |
| 🔐 | 需要登录 |

这条很重要：访客最想知道的就是「我现在不注册能不能用」。逐个功能标，比在开头笼统说一句有用得多。

### 7.3 不写「点击这里」这种一改版就失效的描述

写「顶部导航栏的『插件』」而不是「左边第三个按钮」。**位置会变，语义不会**。

### 7.4 失败路径要写

只说「点提交就成功了」没有价值——用户真正会卡住的是：为什么提交后被退回？
为什么帖子显示「审核中」？每章至少写一条「可能失败的情况」。

### 7.5 不承诺具体时长

不写「审核 24 小时内完成」这类时间承诺，写「审核通过前内容不会公开」。
承诺时长一旦没做到就是失约。

## 9. 站内页面的实现要点

### 9.1 路由与入口

```
/guide              教程页（未登录可访问）
页脚                 加一个「使用教程」链接
```

### 9.2 内容来源

站内页**不要**手抄一份 Markdown 到组件里——两份内容一定会漂。两个方案：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 构建时读 `docs/教程-普通用户与访客.md` 渲染 | 单一真源，但需要 Markdown 渲染链路 |
| B | 站内页只写浓缩版（6 块），文档写完整版 | 实现简单，但要接受两份内容 |

**建议 B**：站内页本来就是「3 分钟看懂」的浓缩版，与完整文档定位不同。
但要在文件头注释里写明「改内容时两处一起改」。

### 9.3 与导航的关系

**不进主导航**（理由见 §3）。页脚链接即可。

## 10. 验收标准

1. **一个没来过的人能照着走通**：首页 → 找插件 → 看评测 → 登录 → 收藏 → 发一条评论，全程不需要问人；
2. **所有 🔐 标记的功能，未登录时真的会跳登录**（逐条点一遍核对）；
3. **没有过时描述**：文中提到的每个页面路径都真实存在（用 `src/app` 的实际路由核对）；
4. **三条通道那条能让人选对**：找三个真实场景（资料写错 / 内容违规 / 站点报错），看教程能否一眼指向正确通道；
5. **没有权限承诺**：不出现「测评员可以……」「开发者可以……」这类尚未上线的能力描述。

## 12. 不适用条件

- 不替代各页面内的即时提示（如表单校验文案）——教程讲「为什么」，页面讲「哪里错了」
