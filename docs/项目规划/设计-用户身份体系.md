# 设计 · 用户身份体系（测评员 / 开发者）

> 状态：设计已定，**尚未实施**
> 迁移：0040（本文档）；当前最新为 0039_favorite_folders_target_kind
> 前置：无。与 PR A（讨论区）、PR B（收藏重构）无依赖关系，可独立实施
> 决策日期：2026-11-06

---

## 1. 目标

站点现在只有两档身份：`user` 与 `admin`（`users.role` 上的硬编码 CHECK）。这个划分无法承载「谁能发评测」「谁的插件算自己的」这类**权限前提**。

本设计引入**可申请的附加身份**：测评员、开发者。它们不是替代 `role`，而是在普通用户之上叠加的能力标记，为后续「某些功能只对特定身份开放」留出依据。

**不做**：企业身份（使用者明确暂缓）。

## 2. 现状与问题

| 项 | 现状 |
|---|---|
| 身份存储 | `users.role TEXT CHECK (role IN ('user','admin'))` —— 只能一档 |
| 身份展示 | `/me/settings` 第 106 行；账户菜单 subtitle（`session-nav.tsx`） |
| 插件归属 | **`plugins` 表没有作者字段**，只有 `repository_id` + `plugin_path`；作者只能从 `repositories.owner_login` 反推 |
| 用户与 GitHub 的关联 | `external_identities.provider_username`（OAuth 登录时写入） |
| 分区角色 | `forum_board_moderators.role(owner\|moderator)`，**分区内生效**，独立于全局身份 |

两个关键缺口：

1. **身份是一档的**，测评员与开发者必须能同时拥有 → 不能塞进 `role`。
2. **插件不知道属于谁** → 「至少有一个本人插件」这条门槛当前无法判定。

## 3. 领域模型

### 3.1 身份（多档并存）

```sql
user_roles
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(id) ON UPDATE RESTRICT ON DELETE CASCADE,
  role_type    TEXT NOT NULL CHECK (role_type IN ('reviewer','developer')),
  status       TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','revoked')),
  granted_by   TEXT REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  granted_at   INTEGER NOT NULL CHECK (granted_at >= 0),
  application_id TEXT,               -- 授予自哪次申请
  revoked_by   TEXT REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  revoked_at   INTEGER CHECK (revoked_at IS NULL OR revoked_at >= 0),
  UNIQUE (user_id, role_type)        -- 一个用户同类身份只有一条记录
);
```

**为什么不是两个布尔列**：`users` 上加 `is_reviewer`/`is_developer` 现在够用，但每加一种身份就要开一列、改 CHECK、重写所有读取点。用表存身份，新增「企业」时只需扩 CHECK 取值。

**`UNIQUE (user_id, role_type)`**：同一用户同类身份只有一条。撤销后再申请**复用同一行**（把 status 改回 active），保留完整的授予/撤销历史在申请表里。

**`role` 保持不动**：`user`/`admin` 仍是权限底座（能否进后台、能否审内容），`user_roles` 只是叠加标记。这样既有的 `isAdmin()` 判定完全不受影响。

### 3.2 身份申请

```sql
role_applications
  id             TEXT PRIMARY KEY,
  user_id        TEXT NOT NULL REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  role_type      TEXT NOT NULL CHECK (role_type IN ('reviewer','developer')),
  status         TEXT NOT NULL DEFAULT 'pending'
                   CHECK (status IN ('pending','approved','rejected','withdrawn')),
  -- 申请时的资格快照（审核时能看到「他当时凭什么申请」）
  evidence       TEXT CHECK (evidence IS NULL OR json_valid(evidence)),
  note           TEXT,                 -- 申请人自述
  reviewer_id    TEXT REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  review_note    TEXT,                 -- 管理员批注（驳回理由）
  created_at     INTEGER NOT NULL CHECK (created_at >= 0),
  reviewed_at    INTEGER CHECK (reviewed_at IS NULL OR reviewed_at >= 0)
);
```

**`evidence` 存资格快照**，不让审核时现算：用户申请的那一刻「有几篇发布评测」「有几个已认领插件」记进 JSON。理由——审核时数据可能已经变了（比如他申请后又删了一篇），逐次重算会让管理员看到与申请人不同的数字，产生争议。同时它也让「凭什么批的」有据可查。

**状态机**：

```
pending ──approve──> approved ──> （写 user_roles）
   │
   ├──reject──> rejected ──(冷却期后)──> 可再次申请
   └──withdraw─> withdrawn ──(无冷却)──> 可立即再申请
```

### 3.3 插件归属（认领机制）

这是本设计最硬的一块。`plugins` 表没有作者字段，而「至少有本人的插件」是开发者的门槛。

**三级判定（使用者裁定：混合方案）**：

```sql
plugin_ownerships
  id            TEXT PRIMARY KEY,
  plugin_id     TEXT NOT NULL REFERENCES plugins(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  user_id       TEXT NOT NULL REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  source        TEXT NOT NULL CHECK (source IN ('github_match','claimed')),
  status        TEXT NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending','verified','rejected')),
  claimed_note  TEXT,              -- 认领说明（如「我是该仓库维护者」）
  reviewer_id   TEXT REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  reviewed_at   INTEGER CHECK (reviewed_at IS NULL OR reviewed_at >= 0),
  created_at    INTEGER NOT NULL CHECK (created_at >= 0),
  UNIQUE (plugin_id, user_id)
);
```

判定规则：

| 情形 | 结果 |
|---|---|
| 用户的 `external_identities.provider_username` 与 `repositories.owner_login` **相同**（忽略大小写） | `source='github_match'`，**自动置 `verified`**，无需审核 |
| 仓库 owner 是**组织**、或用户是协作者而非 owner | 需**认领**：`source='claimed'`、`status='pending'`，管理员审核 |
| 认领被拒 | `status='rejected'`；可重新认领，走同一行 |

**为什么自动匹配的直接放行**：GitHub 账号已经通过 OAuth 绑定（`external_identities`），仓库 owner 与账号 username 相同，这条证据链足够强，再让人审核一遍是浪费。

**为什么组织仓库必须走认领**：``dsh-org/dsh-plugin`` 的 owner 是组织，站内用户没有哪个账号叫 `dsh-org`，自动匹配永远失败。这类作者只能靠「主动声明 + 人工核实」。

**「我的插件」页**：列出 `plugin_ownerships` 中该用户 `verified` 的插件；对未认领的插件提供「这是我的」入口。

### 3.4 分区角色（保持独立）

使用者裁定：区长/协管**不进** `user_roles`。

理由：`forum_board_moderators` 是**分区内生效**的角色——同一个人可能是 A 区区长、B 区普通用户，把它升级成全局身份会让「他在 B 区有什么权限」变得无法表达。

但**展示层可以汇总**：个人中心的「我的身份」一栏可以显示「讨论区区长（综合讨论区）」，数据来自 `forum_board_moderators` 的实时查询，而非 `user_roles`。这样用户看得见，权限判定仍按分区走。

## 4. 资格判定

### 4.1 测评员

> 至少一篇**已发布**状态的测评。

```sql
-- 口径：review 类内容实体已公开、未撤回未隐藏、作者的发布修订存在
SELECT COUNT(*) FROM reviews r
  JOIN content_entities ce ON ce.id = r.id
 WHERE ce.author_id = :userId
   AND r.published_revision_id IS NOT NULL
   AND ce.withdrawn_at IS NULL
   AND ce.hidden_at IS NULL
```

**草稿不算、待审不算、被驳回不算**——只有真正挂出去的才算。（使用者 2026-11-06 确认按此口径。）

### 4.2 开发者

> 至少一个**已验证归属**的插件。

判定依据 `plugin_ownerships` 中 `status='verified'` 的记录，见 §3.3。

### 4.3 两者都满足

使用者裁定：**可以一个一个申请，同时获得两个身份。** 界面不提供「一键双申」，两次申请各自独立审核。

## 5. 页面与接口

### 5.1 页面

| 路径 | 内容 |
|---|---|
| `/me/settings` | 现有身份栏旁加「申请身份」按钮（使用者选定此处，非账户菜单） |
| `/me/my-plugins` | 我的插件：已验证归属的插件列表 + 「这是我的」认领入口 |
| `/admin/roles` | 身份申请审核队列（待审 / 已处理） |
| `/admin/plugins/ownerships` | 插件认领审核队列 |

**「申请身份」弹层**内容：

```
可申请的身份
  [测评员]   条件：至少一篇已发布的测评   当前：已有 3 篇 ✅   [申请]
  [开发者]   条件：至少一个本人插件       当前：已有 1 个 ✅   [申请]
  [测评员]   ——                          已是测评员，无需申请
  [开发者]   条件未满足                  已有 0 个 ❌  [去认领插件]
```

条件未满足时按钮**置灰并说明缺什么**，不给一个点了才知道失败的入口。

### 5.2 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/me/roles` | 我的身份 + 每个可申请身份的资格状态 |
| POST | `/api/me/roles/applications` | 提交申请（role_type） |
| DELETE | `/api/me/roles/applications/{id}` | 撤回申请（仅 pending） |
| GET | `/api/me/plugins` | 我的插件（含待审认领） |
| POST | `/api/me/plugins/{pluginId}/claim` | 发起认领 |
| GET | `/api/admin/role-applications` | 审核队列 |
| POST | `/api/admin/role-applications/{id}` | 通过 / 驳回 |
| GET | `/api/admin/plugin-ownerships` | 认领队列 |
| POST | `/api/admin/plugin-ownerships/{id}` | 通过 / 驳回 |

## 9. 验证

- **资格判定**：草稿 / 待审 / 已撤回 的测评都不算数；只有 `published_revision_id` 非空且内容未撤回未隐藏才计入。
- **插件归属**：username 与 owner_login 大小写不同也能匹配；组织仓库走认领；同一插件不能被两人同时认领为 verified。
- **状态机**：pending 时不能重复申请；被驳回后冷却期内不能再申请；撤回后可立即再申请；撤销身份后可重新申请。
- **多身份**：同一用户同时持有 reviewer 与 developer，互不影响。
- **权限隔离**：`user_roles` 不改变 `role`，`isAdmin()` 行为不变（回归测试必须绿）。
- `tsc --noEmit` + 全量 vitest。

## 11. 未设计部分（明确留白）

1. **撤销身份后的处置**（R5）：撤销后他已有的评测/插件怎么办？是否要连带下线内容？——未设计。当前口径仅「撤销标记」，不动内容。
2. **企业身份**：使用者明确暂缓。
3. **身份带来的具体权限**：「这些身份是后续开放某些权限的前提」——具体开放哪些权限，本设计只提供判定能力（`hasRole(ctx, 'reviewer')`），不定义具体权限点。
4. **管理员主动授予**：当前只有「申请 → 审核」一条路径，没有「管理员直接发」。管理员可以通过自己走一遍申请来变通，但这不是正式通道。

## 12. 不适用条件

- 不改变 `users.role` 的语义与 CHECK，`user`/`admin` 仍是权限底座
- 不替代分区角色体系（`forum_board_moderators`），两者独立
- 不做身份继承或身份组（如「组长能代表组员」）
- 不做身份有效期 / 自动过期
