## ⚠️ 先看这条：本 PR 交付的是**流水线**，不是权限

读完这份描述可能会以为「测评员」「开发者」拿到身份后就能做某些事。**现在还不能。**

实测确认（2026-11-06，全仓 grep）：

- `hasRole()` 与 `listActiveRoles()` **没有任何外部调用**，只在 `roles/service.ts` 内部定义；
- `isAdmin()` 仍然只认 `ctx.role === 'admin'`（`users.role`），**完全不读** `user_roles`。

也就是说：**持有「测评员」身份，在站内不会多开任何一扇门。**

本 PR 交付的是：

| 已交付 | 未交付 |
|---|---|
| 身份的数据模型与状态机 | 哪些功能对哪个身份开放 |
| 申请 → 审核 → 授予与撤销 | 权限点在路由/页面上的实际接入 |
| 插件归属（认领）与资格判定 | 身份带来的任何行为差异 |
| 两个后台审核队列 | — |

**这没问题，但必须说清楚**，否则读的人会以为 `reviewer` 已经能做什么。
后续开放权限的 PR 只需调用 `hasRole(ctx, 'reviewer')`，不必再改本 PR 的任何结构。

## 先说结论

站点原来只有 `user` / `admin` 两档身份，撑不住「谁能发评测」「谁的插件算自己的」这类权限前提。

本 PR 引入两类**可申请的附加身份**：

- **测评员** —— 至少一篇已发布的评测
- **开发者** —— 至少一个已验证归属的插件

身份由用户自己申请、管理员审核后发放，**不自动授予**。两类身份互不冲突，可同时持有。

`users.role` 的语义**完全不变**：`user`/`admin` 仍是权限底座，`user_roles` 只是叠加标记，`isAdmin()` 行为不受任何影响。

设计文档见 `docs/项目规划/设计-用户身份体系.md`。

## 迁移 0040 / 0041

### 0040_user_roles.sql —— 三张表

```
user_roles         身份（user_id + role_type 唯一，可撤销后复用同一行）
role_applications  申请（状态机 pending → approved/rejected，含资格快照 evidence）
plugin_ownerships  插件归属（认领机制的核心）
```

**为什么用表而不是给 users 加布尔列**：`users.role` 是权限底座，测评员 / 开发者是叠加在普通用户之上的能力标记，两者语义不同，混进同一个 CHECK 会让「管理员是不是测评员」这种问题没有答案。用表存，以后加「企业」身份只需扩 CHECK 取值。

### 0041_role_notifications.sql —— 重建 notifications

新增 `role_application_result` / `plugin_claim_result` 两个 kind。

**为什么单独开 0041 而不是塞进 0040**：本分支基于 main，上面没有 0037（未合并的 PR A）。若把 notifications 并集写进 0040，等 0037 合入后会互相覆盖。拆开后各管各的，0041 只负责对齐当时迁移链。

## 插件归属：本 PR 最硬的一块

`plugins` 表**没有作者字段**（只有 `repository_id` + `plugin_path`），而「至少一个本人插件」是开发者的门槛。所以做了两条判定路径：

| 情形 | 处理 |
|---|---|
| 用户 GitHub 账号 = 仓库 `owner_login`（**忽略大小写**） | 自动 `verified`，免审 |
| 仓库属于组织（`dsh-org/x`）或用户是协作者 | 走**认领** + 管理员核实 |

**自动匹配为什么直接放行**：GitHub 账号已通过 OAuth 绑定（`external_identities`），仓库 owner 与账号 username 相同，证据链足够强，再让人审核一遍是浪费。

**组织仓库为什么必须走认领**：站内没有哪个账号叫 `dsh-org`，自动匹配永远失败，只能靠主动声明 + 人工核实。

**一个插件只能有一个 verified 归属人**（部分唯一索引）：否则「我的插件」会出现两个人，开发者身份的门槛就说不清了。但允许多人同时 `pending` 认领，由管理员裁定。

## 页面

| 路径 | 内容 |
|---|---|
| `/me/settings` | 「角色」旁新增「附加身份」+ 申请入口（使用者裁定放这里，不是账户菜单） |
| `/me/my-plugins` | 我的插件：已认领 / 审核中 / 已驳回，认领入口 |
| `/admin/roles` | 身份申请审核队列 |
| `/admin/plugins/ownerships` | 插件认领审核队列 |

**申请面板的五种形态**（判定抽成 `packages/common/roles.ts` 的纯函数，可测）：

```
已持有  → 无按钮，「已是测评员」
审核中  → 无按钮，给「撤回」
冷却中  → 按钮置灰，写明驳回理由与剩余天数
资格够  → 可点「申请」
资格缺  → 按钮置灰，并链到该去的地方（写测评 / 认领插件）
```

条件不满足时**不让用户点了才知道不行**。

后台两个队列：驳回**必须填理由**（前台要展示给用户，空理由等于让人不知道该补什么）。

## 通知与限流

- 身份申请 / 认领的审核结果各发一条站内通知，跳转到 `/me/settings` 与 `/me/my-plugins`
- 通知在**审核事务内**投递，投递失败不回滚审核结论（结论比通知重要）
- 去重键带 result，「驳回 → 补材料 → 通过」各发一条、同一结论重放只发一条
- 新增限流 `role_application`（每天 3 次）：审核走人工，一天内反复改口只会淹掉队列

## 已知缺口（如实列出）

1. **撤销身份后的处置未设计**（设计 §11 明确留白）。当前口径是**只打撤销标记，不动内容**——用户已有的评测与插件一律保留。是否要连带下线内容，等设计给出结论。
2. **管理员没有「直接授予」通道**。当前只有「申请 → 审核」一条路。
3. **撤销理由无处落库**（`user_roles` 没有理由列，也不该改写历史申请表）。接口参数保留以备将来。
4. **身份不改变任何现有行为**（详见上方专节）。
5. **企业身份**暂缓（使用者明确）。
