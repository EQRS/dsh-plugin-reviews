# 第二类收尾：完整数据库模型

状态：已确认；对应架构第 107 节，用户同意进入第三类页面布局。依据 `idea.md`、架构第 1—106 节及 `参数与管理规则.md` 汇总。本文是首版业务物理模型设计，不是已执行迁移；实际认证库私有结构、驱动与部署兼容性在第四类依赖部署中验证。

## 1. 统一表示与约束

字段写为 `字段:类型`，`?` 表示可空，否则必须 `NOT NULL`。`ID` 为规范小写 UUIDv7 的 `TEXT`；`T` 为 `TEXT`；`N` 为 `INTEGER`；`B` 为带 `CHECK IN (0,1)` 的 `INTEGER`；`TS` 为 UTC 毫秒 `INTEGER`；`J` 为通过 `json_valid` 和注册结构校验的 `TEXT`；`E` 为带明确枚举 CHECK 的 `TEXT`。外部 GitHub ID 使用 `T`，不转换成站内 ID。字符串不得用空字符串冒充空关联，必填名称、原因和请求键拒绝纯空白。

以下清单逐表列出全部业务列；只有列出的字段实际存在。`id` 默认主键；没有 `id` 的表另列复合主键。计数、版本、位置及字节数非负，序号和非空发布编号为正；管理、状态、保存版本从零开始，任务重试周期从一开始。时间不得为负。所有 ID 格式、JSON 细分结构及规范摘要由统一契约校验，数据库 CHECK 负责行内条件，不能声称检查 JSON 有效就已校验业务结构。

`created_at/updated_at/submitted_at` 等时间由服务端生成。业务身份不可变；默认外键 `ON UPDATE RESTRICT ON DELETE RESTRICT`。仅第 4 节说明的延迟循环外键使用 `NO ACTION DEFERRABLE INITIALLY DEFERRED`。每个连接在事务外启用 `PRAGMA foreign_keys=ON`，迁移检查外键完整性。不得用关闭外键绕过首次写入顺序。

本文使用 `U(a,b)` 表示联合 UNIQUE，`FK(a,b)→表(x,y)` 表示联合外键，`IDX(a,b)` 表示普通索引。联合外键的父列必须有同顺序、同排序规则的主键或 UNIQUE；子列存在可空项时，通过 CHECK 强制正确成组填写，避免一列为空使整条归属约束失效。所有“必填／全非空”条件生成显式 `IS NOT NULL`，不能仅靠 `a=b` 排除 NULL；未知结果也会通过 SQLite CHECK。除下文已覆盖的复合索引前缀，所有外键子列增加查询索引；服务端不对任意表名开放 CRUD。

| 审核身份／结果 | `user/admin/system`；结果 `pass/needs_changes/manual_review/fault/ineligible`；stage 使用受限注册键。 |
| 事件处理结果 | `delivered/skipped`；未处理时结果及时间同时为 NULL。 |

版本 JSON 沿用架构第 26 节的版本、提交、范围及未知结构，不用字符串 latest 代替未知。安装目标仅接受已注册 npm 固定版本或 GitHub 完整固定提交及真实子路径；显示资料、目标和核验结果分别保存。审核依据、发现进度、备份清单、草稿 payload、来源 data 都有 schema 版本及各自解析器，不共享一个任意 JSON 编辑器。

任务类型、事件类型、通知用途、管理 action、reason_key、字段覆盖 key、存储 variant_key 和 usage 使用首版注册集合。注册集合随应用迁移版本维护并生成 CHECK 或引用固定字典；站点配置可以选择已支持规则，不能自行注入新状态、脚本或 SQL。通知类型只覆盖既定互动及管理反馈，不据此新增提醒渠道。

公共实体 CHECK：review 类型必须 `review_id IS NOT NULL AND review_id=id AND pack_release_id IS NULL`；pack_release 类型必须 `pack_release_id IS NOT NULL AND pack_release_id=id AND review_id IS NULL`。两个子类型回指分别真实 FK→reviews(id)、plugin_pack_releases(id)，采用延迟 NO ACTION。创建时预分配一个 ID，先插入公共实体及其回指，再插入指定子类型，提交时数据库验证没有孤立父记录。子类型的常量类型与作者通过联合外键约束；辅助作者／类型列是关联键，不是独立可修改的业务资料。对这些固定关联禁止 UPDATE。

`reviews` 若 published_revision_id 非空，plugin_id 必须非空，并增加 FK(id,plugin_id,published_revision_id)→review_revisions(review_id,plugin_id,id)。最近提交可指向另一插件的新修订，不能提前修改公开关联。来源确认引用必须属于同一文章；site 当前公开状态要求 source_revision_id 与公开修订一致，在发布／人工确认事务协调，不由作者写来源字段。

隐藏的时间、操作者、原因、操作记录须全空或全部填写；撤回时间与原因成对。整合包已实测要求非空任务及结果；未实测不保留误导的旧实测结论。配置模板存在时要求适用版本结构，允许明确未知；模板不存在时适用版本为空。首次发布在同一事务更新公共发布时间、包计数、版本编号、提交状态和投影；编号只允许 NULL→正整数一次，提交正文及条目始终不可改写。

草稿按类型恰好一个根目标，另一类型目标及起点为空；起点可空，同类型起点非空时必须属于根目标。payload 可暂不完整，正式提交必须生成真实版本与附件关系。历史快照禁止业务 UPDATE/DELETE；必要一次性发布编号和核验结束写入采用明确列白名单及条件更新，迁移不把全文更新当作发布。

审核系统身份需 task_id，人工身份需 actor_user_id；CHECK 禁止全空或错误组合。当前决定由联合外键保证属于当前提交；新增提交先以 NULL 决定建立，追加审核记录后再更新指针，不制造假决定记录。

顶层评论两个回复关联均空；回复两者均非空且不能指自己。创建回复时在同一事务读取已公开目标：root 必须是顶层，parent 若为顶层则 root=parent，若为回复则 root=parent.root。使用受限 BEFORE INSERT/UPDATE 触发器校验这两项跨行固定关系，禁止修改既有评论的目标与回复关系；这样不将跨表 SELECT 塞进 CHECK。评论发布、回复资格及正文可见性由事务服务另行核验，外键不能保证当前公开。

item_type=candidate_check/source_refresh/source_withdraw/metadata_recompute。候选尚未核验时 plugin/repository 可空；来源任务必须填写已知 plugin、source_record、来源 kind/key，业务服务确认 kind/key 与记录一致。带发现依据时 discovery/input/entry 按类型成组非空：发现条目引用明确 entry，缺失撤回只关联完整 input，不虚构不存在的 entry；无发现依据的用户指定检查不填写该组。需要父范围的 input/entry 非空时，CHECK 强制其父列均非空。

发现输入为不可变真实正文 T，而非强迫原始响应一定是 JSON；full_response_data 与 reused_input_id 恰好一个非空。复用记录只指向具有完整正文的基础输入，禁止自引用及复用链，使用受限触发器检查。请求指纹包括来源种类、范围、URL/参数、API 版本、格式及认证可用范围；相同哈希必须再次核对规范请求，不凭哈希碰撞关联。

有效 304 追加本次确认输入，关联匹配的真实完整响应，不更新旧获取时间。输入尝试必须属于发现任务，触发器通过 background_task_attempts→task_id 校验。完整来源选择指针通过联合外键保证同发现；完成服务还要求 input valid、实际解析完整及同一次输入证据。GitHub 多段分页的完整证明按第 97 节保存到注册 progress，不强行用单个页指针表达全站完整；仅完整 Awesome 来源范围可据缺失清单撤回。

安装核验结果 JSON 分开保存可获取性、版本对应性、有效完成及错误；成功依据的有效期按当前配置和匹配指纹计算，不以缓存时间代替核验时间。两种 check_sequence 分别按插件／包条目事务递增，晚到较旧结果只保存历史，不能覆盖更新的生效依据。

## 15. 循环写入、删除与迁移边界

| 场景 | 单事务写入顺序 |
|---|---|
| 评测／包版本首次建立 | 预分配相同 ID→公共实体及延迟回指→对应具体表→必要快照／条目→提交；延迟约束在 commit 检验配对。 |
| 评测修订、评论修订 | 根对象指针先为空→插入所属修订→创建提交及任务关联→更新最近提交指针；首次成功发布后再切换公开指针。 |
| 审核及管理事项 | 主事项 current 指针先空→追加真实决定／处理记录→CAS 更新主事项指针及版本→同步业务变更／审计／事件。 |
| 上传尝试 | 上传记录 active/accepted 先空→插入本次尝试→CAS 设置 active→完整核验后 accepted、received、处理任务一并提交。 |
| 目录调度／发现 | schedule.last_run 可空→轮次→更新 last_run；discovery.selected_input 可空→记录完整输入及条目→完成校验后设置完整指针。 |
| 外部请求 | 先保存 usage→租约绑定 usage→事务外 HTTP→以本 token 更新预算／缓存及释放租约。 |
| 配置启动基线 | 已生成管理员用户／系统身份→基线 configuration_revision→显式 settings；任务引用的配置版本必须已经存在。 |

所有控制写入、发布、计数、去重和事件使用共享事务对象，仓储不得私自另开事务提交一半。使用 SQLite 单主机 WAL，写事务短小；需要判定并写入的流程使用统一写事务/CAS，外部读取、Markdown 解析、图片处理及复制先在事务外准备。忙等待与连接数在依赖部署类别固定，不用无限重试吞掉异常。

核心对象、快照、提交、事项历史、审计、完整输入、回执和备份不物理删除；不配置级联删除。仅明确业务动作可删除当前收藏／投票关系、草稿当前附件关系、字段覆盖项、派生分类关系、搜索投影与当前配置覆盖。被历史引用的文件和存储源禁止直接删除；源退出通过迁移验证和停用业务进行。受限不可变触发器保护快照及历史字段，允许的任务结果结束／一次性元数据更新走白名单，不能提供任意历史编辑接口。

管理员日常只使用既定后台表单、任务和恢复流程。数据库 migration 是部署维护入口。第四类第 109 节提出使用 oauth4webapi 协议工具及本站短期登录挑战表，不引入认证框架的额外用户或会话表；本次补充已随第 109 节确认，实际迁移尚未执行。已有用户、外部身份及会话有效期规则不变。

`oauth_login_challenges` 是本站设计的短期上下文表，不是 oauth4webapi 强制的库表。state 和浏览器绑定摘要不保存原值，verifier 信封包含算法版本、kid、iv、ciphertext、tag，密钥位于部署秘密渠道；return_path 只允许站内相对路径。默认有效期 600 秒由受限部署配置提供。完整核对上下文后以未消费且未到期条件更新 consumed_at，再进行外部交换；用户与唯一 challenge 会话关联在成功事务中建立。首版短期记录不据此启用未经授权的物理清理。

## 16. 配置注册值域与跨参数条件

注册定义存在代码／共享契约中，数据库保存覆盖和完整有效版本。定义必须含 key、类型、范围、默认、说明、权限、生效时点、公开级别及分组校验。以下范围为实施保护边界提案，不是硬件容量或上游承诺；修改超范围须先修改注册实现及迁移定义版本，后台不能任意突破。

| 配置组 | 允许范围／条件 |
|---|---|
| 分页 | page_size 正整数 1—200；允许值集合、默认与最大值相互一致，初值按第 100 节。 |
| 并发／尝试 | 各任务并发 1—32；每周期尝试上限 1—20；初值按第 101 节。总并发不得小于某类型声明并发。 |
| 重试间隔 | 每项 1—86400 秒，非递减；长度与允许自动重试次数匹配，目录下一轮策略单独注册。 |
| 执行权／扫描 | 任务 lease 30—3600 秒；续期／扫描 1—900 秒；续期≤lease/4，扫描≤lease。 |
| 外部请求／任务超时 | 请求 1—600 秒，图片 1—600 秒，单次常规任务 1—3600 秒，长任务无进展 30—86400 秒。内部请求按剩余绝对期限缩短。 |
| 页面进度 | active/waiting 1—300 秒；error_backoff 每项 1—600 秒且非递减。 |
| 会话 | validity_days 1—90；absolute_lifetime_days 1—365 且≥validity；renew_interval_hours 1—720 且小于普通有效期；activity_write_interval_seconds 1—3600。 |
| 接收执行权 | receive_lease 30—3600 秒；renew_interval 1—900 秒且≤lease/4；max_transfer 30—86400 秒且≥lease。 |
| 用户频控 | comment_changes_per_minute、plugin_submissions_per_hour 各 1—1000；窗口单位固定，不通过改键名改变分钟／小时含义。 |
| GitHub 请求 | 两个每分钟上限各 1—300；search≤总量；reserve ratio 有限数值 0≤r<1。上游等待和额度始终更严格者优先。 |
| 缓存及核验 | mutable_cache、commit_cache、install_check_validity 各 1—31536000 秒；过期不自动删除历史。 |
| 读取／导入体积 | Markdown、README 1KiB—20MiB；普通结构响应 1KiB—100MiB；发布包 1KiB—500MiB；条目数量 1—20000；仓库扫描请求 1—1000。现有默认 2MB/10MB/50MB 在实现中统一为 MiB 字节值。 |
| 图片限制 | 需求初值 10MiB／张、20张／篇含封面；大小可配 1KiB—50MiB，数量 1—100；允许类型限定已实现 JPG/PNG/WebP，不能配置启用无解析器格式。 |
| 搜索／预览 | 注册字段权重为有限正数 0.01—100；首页数量 1—100；回复预览 1—50。不能传任意字段名。 |
| 备份 | IANA 已支持时区、合法 HH:mm；首版 retention 固定 keep_all，不提供删除参数。 |
| 其他既有参数 | 草稿保存、目录周期和确认轮数沿用既定初值；时间间隔 1—31536000 秒、确认轮数 1—30。实际名称、单位与注册表逐项一致，不为不存在功能提供配置键。 |

运行中任务和接收尝试使用固定 config_version／快照；后续操作采用新有效版本。账号／内容控制、存储迁移、秘密凭据及字典不塞进普通配置变更。首次 GitHub 主页公开默认是布尔值，只影响新用户。备份计划时区不改变数据库 UTC 时间表示。

## 17. 本类别交接与核对

本类别新明确的物理细节包括：真实头像文件 FK、上传头像专用 scope、公共实体与子类型的延迟配对、跨对象联合 FK、管理反馈的真实处理记录关联、账户状态版本、限流预约及业务频控事实、接收绝对截止、搜索整数内部映射。均落实既有业务和一致性要求，不增加整合包一键导入、评论以外的新互动、永久删除或管理员 SQL 编辑功能。

实施时逐项生成 Drizzle schema、数据库 CHECK／索引／受限触发器及 migration；单元验证至少覆盖缺失子类型、跨文章修订、跨批次输入、错误补充人、旧执行权、禁用后恢复的旧提交、固定快照不可改与 FTS 事务同步。完整应用验收及真实备份恢复属于第五类，不将文档检查当作运行系统验收。

本次设计核对在 Python 自带 SQLite 3.50.4 的 `:memory:` 中完成九组检查：合法延迟配对可提交；孤立父记录、空子类型目标、错误子类型、跨文章公开修订、跨批次输入、错误补充人、缺失头像引用均被拒绝；FTS 投影新增、更新、删除及回滚一致，外键完整性检查无错误。仅验证这些约束机制，没有创建数据库文件；账户版本、全部触发器、任务并发和最终生产驱动尚未据此完成验收。

SQLite 技术依据：[外键与延迟约束](https://www.sqlite.org/foreignkeys.html)、[CREATE TABLE 与 CHECK](https://www.sqlite.org/lang_createtable.html)、[FTS5 外部内容表](https://www.sqlite.org/fts5.html#external_content_tables)。延迟配对、业务分表和配置保护边界是本站设计；最终 SQLite 构建的能力需在依赖部署类别实测。
