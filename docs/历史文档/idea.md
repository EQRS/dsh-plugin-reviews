# DSH Plugin Review · P0 需求说明

更新日期：2026-10-11  
对象：DeepSeek Harness（DSH）插件评测网站  
整理方式：逐点讨论、逐点确认；本文记录本轮确认的首版需求、后续范围与待确认细节。

> 本站独立维护插件目录，通过 GitHub 标签发现与用户提交收录插件，Awesome DSH Plugin 提供补充资料；站点积累站点评测和社区评测，并支持整合包创建、分享与版本管理。

P0 验收范围见第 28 节，待确认项及后续事项集中列在第 29 节。后续候选和未确认提议不自动成为首版开发或验收要求。

最初的大范围方案已保存在 [需求初稿-v1.0-未确认.md](需求初稿-v1.0-未确认.md)。该草案仅作讨论素材，其中尚未讨论的功能、优先级、模板和验收指标均不视为已确认需求。`符` 文件夹中的文档也仅作背景参考。

## 1. 插件目录：独立收录，多来源合并

P0 由本站独立维护插件目录，不以 Awesome 收录或审核通过为前提。数据来源包括：

- GitHub 的 `dsh-plugin` topic：自动发现仓库，基础校验通过后进入本站目录。
- 用户提交：填写 GitHub 仓库或插件子目录链接，触发同样的基础校验，无需等待 Awesome 收录。
- [Awesome DSH Plugin 的公开目录](https://awesome-dsh-plugin.com/plugins.json)：同步已有插件条目，复用分类、简介、安装信息和可选截图，并补齐本站已有条目的资料。

同一插件按仓库与插件子路径关联，多个来源合并为一个条目。缺少或无法确认的安装信息标为“未知”，保留上游说明入口。

自动收录的基础检查：

- GitHub 仓库或指定插件子目录可以访问。
- 对应 `package.json` 有 `dsh.bundle` 声明，且引用的配置文件存在。
- 按仓库与插件子路径检查重复；已有条目则更新资料，不重复创建。

通过基础检查后进入目录，分类和安装信息可以后补。收录表示符合目录基础条件，不代表本站已实际测试可用；实际效果由评测体现。不设 Star 数、提交次数或必须已有评测的门槛。

- 首次拉取完整列表，之后每天自动同步一次，发现新插件并更新已有资料。
- 用户提交仓库或插件子目录链接时立即检查，无需等待每日同步。
- 管理员提供“立即同步”按钮，支持主动刷新。
- 某次同步失败时保留上次成功的数据，记录失败原因，在下一轮重试；页面显示“资料最后同步时间”，以成功同步时间为准。
- 同步目录中已有的名称、简介、作者、仓库地址及其他结构化资料。仓库更新时间等目录未提供的字段，可从 GitHub 补充；缺少时保留未知。
- 站点评测、社区评测及本站讨论数据关联对应插件，由本站单独保存。
- 同步仓库资料时保留本站内容。

仓库归档或不可访问时，保留本站插件页面、历史资料、评测和收藏关联，通过状态提示说明：

- 仓库归档：显示“已归档”，仍可查看资料。
- 连续三轮检查确认无法访问：显示“仓库暂不可访问”，保留上次成功同步的资料；恢复访问后清除该提示。
- 网络超时、接口限流等同步故障：只记录同步失败，不改变插件状态，也不计入确认无法访问的轮次。
- Awesome 移除条目：不直接删除本站条目，继续按本站规则检查仓库状态。

仓库更名或转移给其他作者时，确认属于同一个仓库后，更新仓库地址、名称与作者资料，沿用原插件页面，不创建重复条目。原有评测、评论和收藏继续关联；评测中的被测版本与历史记录保持原样。无法确认新旧仓库关系时交给管理员处理，不仅凭名称相似就合并。

插件列表页提供“提交插件”按钮。登录用户粘贴 GitHub 仓库或插件子目录链接后：

- 已收录：直接跳转到已有插件页面。
- 未收录：立即自动检查，通过后创建插件页面。
- 检查未通过：显示具体原因，允许修改链接后重试。

名称、简介等资料自动读取，缺少分类不阻止收录。提交者无需是插件作者，普通用户也可以补充目录。目录中的仓库子包须保留子路径，避免将同仓库的不同插件合并。

## 2. 插件详情页：介绍与评测

插件详情页提供“反馈资料错误”入口，用户指出简介、分类或安装信息等资料的错误，并附参考链接，由管理员修正。管理员修改过的字段优先展示，后续同步不覆盖；管理员可对单个字段选择“恢复使用同步资料”。P0 采用反馈与管理员修正方式，插件作者自主管理资料留到后续讨论。

每个插件有自己的详情页，先分为两块：

| 区域 | 内容来源 | 内容 |
|---|---|---|
| 插件介绍 | GitHub 同步 | README、作者、源码链接 |
| 本站评测区 | 本站发布 | 实际使用效果、问题、被测版本 |

没有评测时显示“暂无评测”。评测挂在对应的插件页面下，用户可以从该页面进入文章。

## 3. 评测来源：站点与社区

同一个评测区展示两类内容，用明确的来源标签区分：

- **站点评测**：由站点组织，按下述最低要求记录环境、过程和结果。
- **社区评测**：用户提交使用经历，记录被测版本，可在正文补充环境和场景，通过发布检查后展示。

标签说明谁测的、怎么测的。社区评测通过发布审核，不自动代表站点认可其中全部结论。

“站点评测”标签由管理员设置。用户提交的文章默认属于社区评测；站点组织完成的评测由管理员标为站点评测，作者仍显示实际撰写人。管理员自己写的普通使用分享也默认属于社区评测，来源标签表示是否由站点组织，而非作者是否具有管理员身份。

站点评测至少记录三项：

- 测试环境：插件、DSH 版本，以及影响结果的模型或配置。版本字段沿用第 4 节规则，缺少信息时明确标为“未知”。
- 测试过程：用插件完成什么任务、关键操作是什么。
- 测试结果：实际效果、遇到的问题，并附截图、日志或产物等依据。

正文写法自由，由管理员确认上述信息齐全后设置“站点评测”标签。社区评测继续采用自由写作规则，参考模板和补充证据均为可选。

## 4. 版本：专门字段，发布后显示标签

站点评测与社区评测都需要记录版本信息。

| 字段 | 填写方式 | 缺少信息时 |
|---|---|---|
| 插件版本 | 从已同步的版本中选择，也允许手动填写 | 无发布版本时可记录 GitHub 提交；确实不清楚时选择“未知” |
| DSH 版本 | 填写实际使用的 DSH 版本 | 确实不清楚时标明“未知” |

发布后显示类似 `插件 v1.2`、`DSH v0.3` 的标签。版本字段是正文之外的结构化信息，正文可以补充细节。

插件更新后保留旧评测及其被测版本。新版本可以追加评测，旧结论不自动套用到新版本。

版本是否填写或明确标为未知，由表单校验完成，无需人工重复检查。

## 5. 写评测：正文自由，参考模板可选

正文不强制遵循模板。

编辑器提供 **“插入参考模板”** 按钮，点击后插入三个小标题：

- 用它做什么：实际使用场景和任务。
- 效果怎么样：完成了什么、哪些地方有帮助。
- 有什么问题：失败、限制和使用中遇到的坑。

作者可以修改或删除这些标题，也可以直接自由写作。截图、日志、产物属于补充材料，不强制要求每篇文章都提供。

## 6. 编辑器与媒体

### 6.1 正文

- 首版使用 Markdown 编辑器，提供标题、加粗、列表、插图等工具按钮和预览。
- 支持在线撰写和导入 `.md` 文件，也支持批量导入多个 Markdown 文件为草稿，详见第 25 节。
- 导入 Markdown 时可以一并选择包含正文与图片的文件夹，自动匹配本地图片；单独导入 `.md` 时，本地引用的图片可另行补传。具体规则见第 25 节。
- 支持保存草稿和提交发布。
- 独立的富文本编辑器以后按需要再讨论。

评测和整合包共用草稿自动保存能力：停止编辑 5 秒后自动保存，时间可配置；显示“保存中／已保存／保存失败”，失败时可以重试。断网时保留本地临时内容，恢复后同步；重新进入可以继续编辑。自动保存只更新草稿，正式发布仍由作者主动提交。

### 6.2 图片

支持粘贴、拖拽、选择上传，上传后插入正文。图片通过统一存储接口保存，支持对象存储与服务器本地持久目录，本地存储作为保底实现；上传后生成压缩展示图。

本站托管图片使用固定的站内访问地址，文章不绑定某个存储源的域名或临时链接。启用多个存储源时，同一图片及同一尺寸版本在各源的内容必须一致，本地保底须保存实际文件副本。切换来源前完成复制与完整性校验；迁移期间旧图片继续从仍可用的原来源读取，不能只改配置就停用尚有未迁移文件的旧源。管理后台提供存储状态、迁移进度、失败原因和重试入口，切换后原文章图片链接继续可用。此要求针对本站托管图片，导入保留的外部图片链接仍由其来源提供。

首版默认支持 JPG、PNG、WebP，单张最多 10MB，每篇评测最多 20 张图片，单独上传的封面也计入。超过限额时明确提示原因。允许的格式、单张大小及每篇数量均作为可配置项，后续根据实际使用和存储费用调整。服务提供商和费用尚未确定。

### 6.3 视频与其他材料

- 视频先使用 B 站等平台链接，首版不接收视频文件。
- 日志和代码可以放正文代码块，或提供 GitHub 链接。
- 首版不开放任意文件附件上传。

## 7. 登录与本站用户资料

浏览无需登录；发布评测需要登录。首版优先采用 GitHub 登录。

站点保存自己的用户记录，至少包括：

- 本站用户 ID 与关联的 GitHub 身份标识。
- 昵称、头像。
- 角色和账户状态。
- 注册时间，以及该用户关联的文章、草稿等内容。

首次 GitHub 登录时自动创建本站用户。账户关联使用稳定的身份标识，修改昵称不改变内容归属。

首次登录提供可跳过的 **“确认站内资料”** 页面：

- 昵称预填 GitHub 昵称，用户可以修改。
- 头像默认使用 GitHub 头像，用户可以更换。
- 用户选择是否公开 GitHub 主页链接。
- 用户可点击“使用默认资料”继续，以后在个人设置里修改。

后台保留 GitHub 身份关联；公开展示资料由用户选择。GitHub 主页公开初始值已确认为关闭，用户可选择公开，见架构第 106 节。

P0 包含插件与整合包收藏，具体范围见第 15 节。

## 8. 入口与草稿：从插件页直接写

用户在插件详情页点击 **“写评测”**，打开已经关联当前插件的编辑器。

- 插件关联由站点自动完成，用户无需再次选择。
- 保存草稿后，草稿进入个人中心，只有作者可查看和继续编辑。
- 点击“提交发布”后，才进入发布检查流程。
- 用户可在个人中心查看处理状态和需要补充的原因。

对应插件由页面上下文和数据关联保证。版本填写由表单校验保证。人工审核主要处理内容疑问，例如正文是否跑题。

## 9. 发布检查：自动初审，疑难转人工

已讨论的发布方式为：

```text
保存草稿 → 提交发布 → 自动检查
                         ├─ 符合发布条件 → 发布
                         ├─ 缺少资料 → 提示作者补充
                         └─ 有疑问 → 人工审核
```

自动检查分为：

- **规则校验**：必填字段、附件类型及大小、明显重复提交。
- **内容筛查**：AI 辅助识别跑题、广告及不适合公开的文字和图片。

审核服务出错时保持“待审”，支持用户申请人工复核。需要修改时说明原因，作者补充后重新提交。好评与差评使用同样的发布规则。

自动放行条件统一为：必填资料、内容关联和附件检查通过，且内容筛查无疑问时自动发布；缺少资料或有明确需修改的问题时列明原因，提示作者补充；内容判断有疑问时转人工，审核服务故障时保持待处理。该边界适用于评测、整合包及评论，各类型按已确认的必填规则检查。未知版本、未实测、负面评价本身不构成拒发理由。检查规则及对应处理方式集中配置，调整时保留记录。

发布检查判断内容是否符合发布条件；评测结论是否真实可靠仍需结合证据。AI 服务及检查规则的具体实现留到技术设计阶段，管理员后台范围见第 23 节。

## 10. 发布后修改与撤回

作者可以修改自己的评测：

1. 修改先保存为草稿，原公开版本继续展示。
2. 提交修改后，走同一套自动检查；有疑问的转人工。
3. 通过后更新文章，显示最后修改时间，保留修订记录。

评测插件新版本时，编辑器提示选择“更新原评测”或“另写一篇”，方便保留旧版本经历。

作者可以撤回已发布评测。撤回后退出公开列表，原链接显示“作者已撤回”，正文和评论不再公开；内容保留在作者个人中心，可以修改后重新提交发布。插件的评测数量只统计当前公开的文章。

P0 对读者展示发布时间、最后修改时间与当前被测版本。完整修订记录保留，作者和管理员可以查看，用于找回内容和处理争议。读者查看旧版正文、比较修改差异留到后续讨论。

永久删除的规则尚未讨论。

## 11. 评测评论与回复

每篇评测下支持评论与回复。登录用户可以追问使用细节、补充自己的结果，评测作者也可以回复。

首版采用“评论＋回复”的简单结构，讨论关联到对应评测。

评论与回复沿用“自动检查，疑难转人工”的发布方式：

- 正常内容通过检查后直接展示。
- 明显广告、重复刷屏等提示修改；有疑问的转人工。
- 检查服务故障时保持待处理，用户能看到处理状态。

评论只需填写正文，不要求评测模板或版本信息。追问、反驳和差评使用相同规则，不因意见负面而拦截。

用户可以修改自己的评论，修改通过同样的发布检查后替换原文，显示“已编辑”。修改检查期间原公开内容继续展示。

用户可以删除自己的评论；已有回复时保留“该评论已删除”占位，回复继续保留。管理员可以隐藏违规评论并记录原因；评测作者不能删除别人的评论，可以举报。

P0 提供站内通知：评测收到新评论时通知评测作者，评论收到回复时通知被回复的人。内容通过检查并公开展示后才发送通知；自己回复自己不通知，同一事件不重复通知。顶部显示未读数量，点击通知跳到对应评论。邮件和浏览器推送留到后续讨论。

## 12. 插件页的评测列表

默认按发布时间从新到旧排列，提供两个筛选维度：

- 来源：全部／站点评测／社区评测。
- 插件版本：查看对应版本的评测。

每条评测显示标题、作者、被测版本和发布时间，点击进入正文。站点评测使用来源标签区分，默认列表仍按时间排列。

## 13. 评测的“有帮助”反馈

每篇评测提供“有帮助”按钮，登录用户一人一票，可以取消。

数量关联到评测文章，表示读者认为文章有参考价值，不作为插件综合评分。后续可增加按有帮助数排序，当前默认仍按发布时间排列。

插件打星和综合评分留到后续，P0 展示具体评测、被测版本及文章的“有帮助”反馈。积累足够评测后，再讨论按版本评分、评分维度和最低样本数，避免将不同版本、不同使用场景下的表现直接合成一个分数。

## 14. 配套 DSH 导入插件：排除在 P0 之外

配套 DSH 导入插件，以及依赖它实现的网站一键导入功能，列为后续讨论事项，不纳入 P0 开发或验收，也不构成首版上线前提。整合包创建、分享及可选配置模板纳入 P0，具体范围见第 26 节。

后续候选方案：整合包记录插件清单、固定版本、组合配置及适用的 DSH 版本；配套导入插件读取整合包，在 DSH 内经用户确认后安装并应用配置。具体实现、导入入口、发布方式和安排尚未确定。

普通插件的安装资料纳入 P0，优先使用公开目录提供的结构化信息，详情页提供复制安装命令及查看上游说明的入口。安装信息缺少或待核实时只保留上游说明入口；资料核验与实际安装实测分别标注。

整合包也支持收藏，沿用插件收藏的操作方式。个人中心区分“收藏的插件”和“收藏的整合包”。收藏关联整合包本身，进入时默认查看最近仍公开的版本；仍公开的旧版本可从历史版本中找到，作者发布新版后无需重新收藏。撤回时的显示规则见第 26 节。

## 19. Awesome DSH Plugin：已采用的数据来源与调研依据

用户提供参考站点：[Awesome DSH Plugin](https://awesome-dsh-plugin.com/zh/)。讨论后确认：本站独立收录插件，GitHub 标签发现与用户提交不依赖 Awesome 审核；Awesome 公开目录用于同步和补齐资料。前文对应需求已按此调整。以下为调研依据：

- 项目使用结构化插件条目；其收录检查包含 `package.json` 的 `dsh.bundle` 声明。见 [贡献指南](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/contributing.md)。
- npm 探测读取仓库的包名，检查 npm 包存在且其仓库地址对应原仓库，再记录映射。见 [探测脚本](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/scripts/probe-npm.mjs)。
- 生成脚本发布包含分类、描述、npm 包映射、安装命令和可选截图等信息的公开目录；安装命令来自结构化信息。见 [生成脚本](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/scripts/build-site.mjs) 与 [目录地址](https://awesome-dsh-plugin.com/plugins.json)。本次未逐条核验全量目录。
- 项目目录采用 [CC0 许可](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/LICENSE)，生成脚本明确提供面向第三方网站的公开目录接口；读取和复用目录无需先申请收录。让插件进入 Awesome 自身目录则需要按贡献指南提交 PR 并等待审核。目录许可不替代各上游插件代码及内容的许可。

本站单独保存评测、用户与收藏，同步不得覆盖这些数据。独立收录的基础检查、同步频率、同步失败及仓库更名／转移／归档／不可访问的处理见第 1 节。

由此修正此前的讨论建议：复制安装命令可以通过结构化资料自动生成，不必依赖从 README 提取命令；资料核验与真实安装实测需分别标明。配套 DSH 一键导入插件仍排除在 P0 之外。

## 23. 管理员后台：纳入 P0

提供统一的待处理事项列表，区分评测审核、整合包审核、评论审核、举报、资料纠错和复核申请。每项显示对应内容、触发原因及用户补充材料。

管理员根据事项执行通过、退回修改、隐藏或修正资料，并记录处理原因。已处理事项进入历史记录，方便追查；需要反馈给用户的处理结果沿用站内通知。

日常数据管理通过后台业务页面完成：插件资料修正及恢复同步字段、评测来源标签、内容审核与隐藏、分类与模板维护、业务配置调整、管理员权限管理，以及已确认的同步和批量导入任务，均提供对应操作入口。管理员无需为这些操作手动修改数据库表。表单提供业务名称、关联对象选择和有效值校验，关联数据更新、状态变化及操作记录由服务端统一处理；处理失败时说明原因，任务进度可查看。

P0 只区分普通用户和管理员。GitHub 首次登录默认是普通用户，首个管理员在部署时指定 GitHub 身份。后续由现有管理员授予或撤销权限，并保留操作记录；系统确保至少保留一个管理员。审核、纠错、同步和设置站点评测标签均由管理员处理，首版不细分多个管理角色。

## 24. 整体原则：尽量可配置，数据驱动

能合理配置的业务参数与资料尽量通过配置或数据管理，避免散落在代码中。前文已确认的参数作为首版默认值，而非永久固定值。

- 业务参数：图片格式、单张大小、每篇数量、草稿自动保存间隔、同步周期、确认仓库不可访问的检查轮次等集中配置，常用项由管理员在后台调整。
- 业务资料：插件分类、用途标签及映射、可选参考模板等以数据形式维护，页面与表单读取对应数据。
- 部署配置：GitHub 登录、存储、审核服务和首个管理员等相关设置通过服务端部署配置管理。

配置有默认值、有效范围与修改记录。前端提示和服务端校验使用一致的配置；业务配置更新后按新配置处理后续操作，不自动删除既有内容。尚未确定的参数和规则继续逐点讨论。

具体数据结构设计时，抽象统一的“可评论对象”父类／公共实体。评测文章与整合包发布版本作为具体对象，评论统一关联公共对象 ID，回复关联对应评论。评论的发布检查、修改删除、举报和通知共用一套能力；整合包以发布版本作为评论对象，保留版本间的讨论边界。具体字段与表结构在技术设计阶段确定。

后续代码实现需重视架构设计、抽象与封装、可扩展性和可维护性：

- 按业务职责划分模块，明确模块边界、接口和依赖关系；以实际业务变化点为依据抽象公共能力。
- 评论、审核、通知、配置等共享能力集中封装，各业务通过明确接口使用。
- GitHub、Awesome 目录、对象存储及审核服务等外部依赖通过适配接口接入，便于替换或扩展数据源与服务。
- 业务规则与页面展示分离，相关规则集中维护；数据结构、状态变化和错误处理保持一致，并保留必要的操作记录。
- 数据操作按业务封装，后台管理与网站功能共用业务服务；日常管理操作不要求管理员直接操作数据库表，表结构升级通过受版本管理的部署迁移入口执行。

进入具体开发前先形成架构与数据设计说明，明确模块职责、数据关系、关键流程及扩展位置，再推进实现。具体技术栈与实现方式在技术设计阶段确定。

## 25. 批量导入、集中投稿与审核队列：纳入 P0

建站初期由管理员启动插件资料批量导入任务，逐条执行基础检查、合并重复条目，并显示进度和失败原因。

作者可以批量导入 Markdown 文件为私有草稿，确认后统一提交。每篇文章进入审核队列，独立显示处理结果；某篇失败不影响其他文章。

导入后显示待确认清单：从插件页面导入时，全部默认关联当前插件，提交前可以修改；从个人中心导入时，可以选中多篇统一关联一个插件，也可以逐篇搜索选择。尚未关联插件的文章保留为草稿，关联完成后才能提交审核。Markdown 正文自由，不要求特殊文件名或正文格式。

支持选择包含 Markdown 和图片的文件夹，只读取 Markdown 及其引用的支持格式图片。按相对路径匹配本地图片，上传后自动替换正文链接；找不到或超限的图片列出具体原因，作者可以补传、替换或移除引用。网络图片和视频链接保留原链接。导入后先预览、保存为草稿，确认无误再提交；图片限额沿用站点配置。

批量导入任务保存进度。断网或关闭页面后，已生成的草稿保留，已上传完成的文件继续由后台处理；未上传完或处理失败的项目单独列出，允许重新选择文件后重试。作者可以在个人中心查看任务进度和逐篇结果；重试不重复创建已有草稿。

不采用此前提出的“评测每人每小时最多提交 10 次”的硬上限。提交频率控制侧重重复请求，审核服务按可配置的速度处理队列，并在不同作者的任务之间轮流安排，避免单个作者的大批投稿持续占住处理能力。作者可以一次提交齐全，无需按小时分批回来提交。

评论变更每用户每分钟 5 次、新的指定插件提交检查每小时 10 次已在架构第 106 节确认，具体统计、重复请求及配置规则见 `参数与管理规则.md`；不限制评测每小时篇数。

## 26. 整合包：创建与分享，纳入 P0

整合包是一份可分享的插件组合，包含名称、用途、插件清单及对应版本，以及解释插件如何配合的组合使用说明。例如“科研资料整理套装”。

整合包另有独立的 DSH 版本字段，每个整合包发布版本单独保存。记录作者制作或实际使用该组合时的 DSH 版本，不清楚时明确标为“未知”；在详情页显示版本标签，正文可以补充适用条件。记录某个 DSH 版本不自动表示该组合已实际测试，也不自动宣称兼容其他版本。

清单中的插件版本复用评测的版本选择能力：从同步到的版本中选择，也允许手动填写；没有发布版本时可以记录 GitHub 提交；确实不清楚时标为“未知”，详情页提示该项版本尚未确认。记录该组合采用的版本，不自动替换成插件最新版。

整合包清单中的每项同时保存版本和实际安装来源，以及对应的安装标识（spec），用于生成与该版本对应的安装命令。npm 来源记录包名与明确版本，GitHub 来源记录仓库、插件子路径及固定提交等资料；展示版本与实际安装目标保持关联，具体字段在数据设计阶段确定。

生成安装命令前核验目标资料：npm 来源检查对应包和版本，GitHub 来源检查提交及插件目录。信息确认后提供“复制安装命令”；无法确认时标为“待核实”，保留来源链接。已发布整合包的安装来源失效时显示提示，由作者修正并发布新版，不自动替换为最新版。该检查只针对安装资料，组合实际效果仍由实测说明。

详情页按插件清单顺序展示已核实的安装命令，支持逐条复制与“复制全部”。存在待核实或失效项目时，明确列出哪些项目未生成命令，并在批量复制前提示。配置模板另行复制，并附配置步骤；用户在自己的 DSH 环境执行命令。

创建时搜索本站插件目录，选中后加入清单；未收录的插件可以粘贴仓库链接，按已有规则执行收录检查，通过后加入。清单可以调整顺序，每个插件可选填一句在组合中的作用说明。插件清单通过表单维护，组合使用说明使用 Markdown 编写。

P0 提供创建、编辑、发布、分享和查看历史版本。每个整合包有独立页面，创建者可以编辑，其他用户可以查看、分享，并进入各插件页面了解评测和安装方式。一键导入、自动安装及自动应用配置继续留到后续，见第 14 节。

个人中心提供“我的整合包”入口，先按整合包展示，进入后查看各版本。每个版本显示草稿、待处理、已发布或已撤回状态，以及需要补充的原因。编辑草稿、提交发布、创建新版和撤回版本均从此处操作，同一个包的版本集中管理。

配置模板为可选项，只提供插件清单和使用说明也能发布整合包。需要特定配置才能配合使用时，可以附配置模板，注明适用的 DSH 版本。API Key、密码等用占位符表示，由使用者在本地填写。先支持查看、复制配置模板，自动应用配置随一键导入功能留到后续。

整合包拥有自己的发布版本，每次发布保存当时的插件清单、对应插件版本和配置模板。作者修改后发布新版，旧版保留历史记录，未撤回的旧版仍可公开查看；页面默认展示最近仍公开的版本。插件上游更新时提示作者有更新，由作者确认后发布新的整合包版本，不自动改变已经发布的组合。

作者可以逐个撤回整合包版本。撤回后，该版本的清单、配置和评论不再公开，原链接显示“作者已撤回”。默认展示最近仍公开的版本，并提示新版被撤回；全部版本撤回时，整合包退出公开列表，收藏保留并显示状态。作者仍可查看撤回内容，修改后发布为新版本。

整合包提供评论与回复，用于反馈安装问题、组合效果和配置疑问。评论关联具体整合包版本，页面默认展示当前版本的讨论，也能切换查看旧版。登录、发布检查、修改删除、举报和回复通知沿用第 11 节规则，整合包作者收到新评论时获得站内通知。数据结构按第 24 节抽象公共的可评论对象。

整合包的实测状态默认为“未实测”。作者实际运行过组合后可选择“作者已实测”，并补充测试任务和结果，截图和日志可选。该标签随整合包版本保存，新版本需要重新确认；标签表示作者声明，站点发布审核另按内容规则处理。

整合包发布沿用统一流程：保存草稿 → 提交 → 自动检查 → 发布／提示补充／转人工。检查名称、用途、插件清单和版本字段是否齐全，再对说明、图片和可选配置模板执行内容检查；版本字段可以明确标为“未知”。“未实测”或部分安装资料“待核实”的整合包仍可分享，页面清楚展示相应状态。发布新版也走同一流程，疑难事项进入统一管理员后台。

指定插件版本的安装能力已查证：DSH 的 `dsh plugin --profile <name> <args...>` 将参数转发给 pnpm，npm 来源支持 `包名@明确版本`，可加 `--save-exact` 保存精确版本依赖；GitHub 来源可使用 `github:owner/repo#<完整提交SHA>` 固定提交。见 [DSH 官方安装说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md) 与 [pnpm add 文档](https://pnpm.io/cli/add)。官方插件管理界面也接受带版本的包名，见 [插件管理界面说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-plugin-manager/README.zh.md)。此为文档查证，未进行实际安装测试；目标版本必须仍可获取，GitHub 源码还需满足构建与安装条件，指定版本不自动保证与所记录的 DSH 版本兼容。

## 27. 整合包列表：纳入 P0

提供“整合包列表”入口，汇总当前公开的整合包，默认按最新发布时间排列。支持按名称和用途说明搜索。

整合包用途标签、作者选择标签以及按标签筛选均留到后续，不纳入 P0。P0 保留名称、用途说明与关键词搜索。该范围调整仅针对整合包标签，不影响插件目录已确认的分类与筛选。

每条显示名称、用途简介、作者、插件数量和最近仍公开的包版本，点击进入详情页。详情页展示完整清单、可选配置模板、仍公开的历史版本和对应版本的评论。

## 28. P0 上线验收范围

按四条完整流程验收，覆盖前文已确认的相关需求：

| 流程 | 验收范围 |
|---|---|
| 浏览 | 找到插件、搜索评测、查看整合包及安装资料；搜索、筛选和详情入口指向对应内容，公开列表只展示公开内容。 |
| 创作 | 保存与恢复草稿、批量导入、提交审核、发布、修改和撤回；版本关联、逐项处理结果与历史保留符合已确认规则。 |
| 互动 | 评论回复、收藏、举报和站内通知；操作关联正确的文章或整合包版本，处理结果和未读通知可查看。 |
| 管理 | 人工审核、资料纠错、同步和配置调整；处理结果、失败原因及操作记录可查看，修改后的配置按规则生效。 |

每条流程同时检查：

- 权限：匿名浏览、作者私有草稿、本人编辑权限与管理员操作权限符合既定范围。
- 失败提示：同步、上传、导入、保存或审核失败时显示明确状态与原因，按对应流程提供已确认的重试或复核入口。
- 数据保留：同步失败保留上次成功资料，导入重试不重复创建，撤回或隐藏的内容不再公开，历史版本与关联数据按既定规则保留。

进入实现后，按上述流程记录验收结果；未确认功能不计入 P0 验收。分阶段安排和具体故障验证见 [实施顺序与验收](实施顺序与验收.md) 及架构第 110 节，当前待确认，验收尚未执行。
