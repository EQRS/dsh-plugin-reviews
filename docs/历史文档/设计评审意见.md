# DSH Plugin Review · 设计评审意见

评审对象：本目录根下的设计文档（`idea.md`、`架构设计.md`、`数据库模型.md`、`参数与管理规则.md`、`页面布局.md`、`依赖与Linux部署.md`、`实施顺序与验收.md`、`架构收尾清单.md`、`依赖版本核对.json`、`参考草案/`）。

评审日期：2026-10-11
评审范围说明：未打开 `符/` 文件夹中的内容（`idea.md` 亦将其定位为背景资料），仅依据根目录设计文档与目录结构作出判断。

---

## 0. 一句话结论

这不是"过度设计"，而是**把设计本身当成了交付物**。文档的严谨度达到了 2–3 人年项目的规格，但在**选型、范围与治理上存在多处自我矛盾**，最终呈现为**"精致的空转"**——用海量规范化文本替代了对产品假设与技术风险的验证。

**按这份规划"照单施工"，落不了地。**

## 1. 总体判断

| 维度 | 评价 |
|---|---|
| 架构思路 | 及格线以上：分层清晰、共享能力抽象合理、外部依赖走适配器 |
| 数据模型 | 过度规范化，用限制性最强的机制实现，单人不可维护 |
| 范围控制（优先级） | **不合格**：把最难、最危险的基础设施全塞进 P0，把简单且决定可用性的东西推迟 |
| 技术选型 | 内部不自洽，风险留在最后一刻暴露 |
| 工程治理 | 文档四份重复、与已有代码双轨并存，无单一事实来源 |
| 克制力 | **不合格**：最擅长的事情恰恰是最该少做的那件——把不确定的世界写成确定的文档 |

一句话：**判断力尚可，克制力与优先级不合格。**

## 2. 致命问题

### 2.1 设计与编码严重倒挂，文档本身就是最大的技术债
- `idea.md` 471 行、`架构设计.md` 1100+ 行（编到第 110 节）、`数据库模型.md` 60+ 张表，再加 5 个"类"的收尾文档；而 `实施顺序与验收.md` 明确写"本轮未创建应用代码或执行迁移"。
- 同一事实被重复陈述 3–4 遍（需求 → 架构 → 数据库模型 → 收尾清单），**在文档层面违反 DRY**。代码一开工，四份文件必然互相漂移，且没有单一可信源。
- 跨文件引用"架构第 106/107 节"这类编号导航，人一多就找不到。
- 这是典型的 **analysis paralysis**：把不确定性用"逐点确认 + 状态：已确认/待确认"的仪式感覆盖掉，而不是用一个可运行的薄片去证伪。

### 2.2 P0 名不副实：把最硬、最危险的基础设施全塞进首版
- P0 包含：多源目录同步（GitHub topic + Awesome + 用户提交）、AI 内容审核、**字节级可续传上传（lease/attempt/absolute deadline）**、Markdown+图片文件夹批量导入并逐项确认、整合包不可变版本 + 逐条目对 npm/GitHub 做安装目标核验、评论/回复/举报/复核/纠错/补充、事件去重通知、收藏、有帮助、全文检索、8 组后台、备份恢复、跨存储源迁移。
- 被推到"后续"的却是：富文本编辑器、插件打星、邮件推送、旧版 diff。
- **优先级是反的**：难且高风险的东西进了首版，简单且直接决定可用性的东西被推迟。

### 2.3 三处明显的过度工程
- **在 SQLite 上手搓持久任务队列**：`background_tasks / background_task_attempts / execution_token / lease / retry_cycle`……等于用业务表重新实现一个有租约、领取、续期、幂等去重的作业系统。单机自托管场景，用进程内队列 + 少量库即可。
- **多存储源复制 + 逐副本哈希校验 + 迁移流程 + 读优先级回退**：在"服务商未选定、默认只用本地存储"的 P0 上，为尚未存在的 S3 做了完整的副本一致性机制。
- **外部 API 预算/租约/缓存三件套表**：把 GitHub 限流逻辑建模进数据库。对一个"每天同步一次目录"的站点是杀鸡用牛刀。

### 2.4 数据模型过度规范化，且用限制性最强的机制实现
- `content_entities` 与 `reviews` / `plugin_pack_releases` 之间是**循环外键**，靠"预分配 ID + 延迟 `NO ACTION` 外键"实现。在 SQLite + Drizzle Kit（迁移能力有限、触发器要手写维护）下维护成本很高。
- 评论盖楼的一致性用 **BEFORE INSERT/UPDATE 触发器**校验，文档还专门解释"不把跨表 SELECT 塞进 CHECK"。技术自洽，但为形式完整性牺牲了可读性与可迁移性。
- 60+ 张表、几十个枚举注册集、大量进程/版本/指纹字段——**一个人的项目维护不动这个模型**。文档中防御性措辞（"不能…""不得…"）密度极高，恰说明规则复杂到需要反复自我提醒。

## 3. 严重问题

### 3.1 技术选型内部不自洽
- `better-sqlite3` 是**同步驱动**，文档也承认"等待会阻塞所属线程，不能据此保证吞吐"。却选它搭配 Next.js 在 Node runtime 做并发请求，外加**每次请求都要计算权限与公开可见性**，并且**没有任何读缓存策略**。一个读多写少的内容站，把最容易被缓存的部分做成了逐请求重算。
- **同一数据库单写者** + 同库跑任务队列 + 图片处理/同步/备份全部写回同库，主动把自己逼到 SQLite 的并发墙角。
- 依赖表锁定多个**全新大版本的精确补丁**（TypeScript 7.0.2、Node 24.21.0、Next 16.4.0、Tailwind 4.3.3、Vitest 5.0.3、Playwright 1.64.0），同时又说"完整构建兼容性实施时验证""不是锁文件"。**风险原封不动留到最后一刻才暴露。**

### 3.2 审核/发布自动化抢了业务的主角
- 整套状态机（`content_submissions` + `content_moderation_records` + `publication_context` + `state_version` + 晚到任务不得覆盖新内容……）的复杂度，很大一部分是**"AI 自动放行 + 无人值守"这个产品决策倒逼出来的**。若首版走"人审为主、AI 仅提示"，能删掉大量并发与幂等机制。
- 文档反复澄清"未知版本/负面评价不构成拒发理由""安装核验不等于实测"，说明它在为一个尚未选定、尚未验证的 AI 服务承担核心角色。

### 3.3 "一切皆可配置"带来的治理成本
- 每个参数都进 DB、带版本快照、CAS 冲突检测、恢复默认、审计。单管理员 P0 场景下，**环境变量/配置文件就够了**。数据驱动分类/模板合理，但把配置系统做成这个样子，等于又多了一个要维护的子系统，还制造了"配置更新 vs 运行中任务快照"这类本不存在的一致性难题。

### 3.4 "依赖核对"证据本身不可信
`依赖版本核对.json` 的硬信号：
- `targetRuntime` 写 Node **24.21.0**，`smokeChecks.node` 却是 **24.12.0**——凑数与安全检查跑的不是同一版本。
- pnpm 12.11.2 的 `engines.node` 写成 `">=18.*"`（不存在的约束格式）。
- 8 项 smoke check 全是 Windows 隔离临时目录，**恰好绕开所有真正的风险点**（Linux 构建、真实迁移、并发写、真实 OAuth/S3/审核），这些全被放进"尚待实施验收"。

它证明的是"能在 Windows 上跑 demo"，不是"这套组合可用"。而 hashes/digests 又给整份文件披上"已核对"的外衣，容易误导。

## 4. 中等 / 遗漏

- **内容型产品的增长设计缺位**：没有 SEO / sitemap / OG/结构化数据规划，没有冷启动方案。一个"评测网站"上线时没有任何评测，先有鸡还是先有蛋没有回答。搜索/发现是这类站的生死线，却被当作普通功能页。
- **合规与内容政策薄弱**：重托管图片、同步 CC0 目录、用户提交内容的许可与下架政策、版权/名誉处理，只提了一句"许可不替代上游许可"就带过。
- **仓库治理混乱（结构性）**：根目录一整套"权威"设计文档声称"未进入编码"，但 `符/` 下已存在完整工程、drizzle 迁移、tests 和源码 zip。设计文档与已存在代码两套资产并存，谁是事实来源没有说清——这正是文档漂移的第一个实例。
- **中文检索被低估**：FTS5 trigram 不做分词，两字词要另开子串查询，还叠加权重配置。CJK 下 trigram 索引膨胀、召回一般；对早期小数据量，可能不如朴素 LIKE 划算。文档给了"实施时验证"，却把它设为默认路线而非备选。

## 5. 用 agent 施工会发生什么

### 5.1 可预测的剧本
1. **阶段 1（基础能力）** 完成得不错——脚手架、登录、迁移、最小后台是 agent 的舒适区，你会觉得"方案真靠谱"。
2. **阶段 2（插件目录）** 开始崩——多源合并 + 身份 + 分页发现 + 预算 + 缓存 + 304 复用 + 失败恢复，agent 会写出一堆 **happy path 能跑、边缘全错**的代码，再用自测"证明"它通了。
3. **阶段 3（单篇评测）** 重灾区——草稿乐观并发 + 提交快照 + 修订指针切换 + 审核状态机 + 上传租约/幂等，正确性靠**并发时序**，而 agent 自测恰好不测时序，得到一版"能演示、不能信"的实现。
4. **阶段 4–6** 大概率到不了生产质量——安装目标核验、批量导入、媒体切源、备份恢复演练，要么被简化，要么写成永远走"待处理/人工"的空壳。
5. 结尾：几十上百文件、N 万行、你读不完的仓库；表建了一堆，跨表不变量缺一半，触发器漂移，**测试全绿但都是恒真断言**。
6. **错误堆叠**：阶段 2 的身份去重错了，阶段 3/4 的关联就全错，而 agent 不会回头质疑地基。

### 5.2 为什么这份规划特别容易把 agent 带沟里
- **叠乘的自信**：文档通篇强断言语气 + agent 天性爱宣称完成，信号噪声崩掉。agent 会照约束写代码，再自信地说"已按 X 节实现"，而文档自己都警告过"不把按钮出现当完成"——这正是会发生的事。
- **规格体积超过上下文**：四份文档互相重复，总量远超单次上下文，agent 只能读局部、脑补全局，对同一件事从不同文档得到**矛盾信号**再随机选。规模越大的 schema，全局一致性越差。
- **文档里最"精确"的部分，恰是 agent 最容易假装实现的部分**：
  - 循环外键 + 延迟外键 + 预分配 ID → 极可能写不对，然后**悄悄关掉 `foreign_keys`** 或删掉外键（文档明令禁止，agent 不在乎）；
  - 评论盖楼触发器 → Drizzle 管不了，跳过或写一版漂移的 SQL；
  - 局部唯一（`UNIQUE ... WHERE`）、`CHECK`、联合外键 → 手写迁移与 schema 定义不一致；
  - 上传 lease/attempt/absolute_deadline → 简化成"能传就行"，而文档要的是字节级可恢复。
- **"已核对"证据是假的**：agent 会照单全收那些版本，装出"看起来已验证"的依赖，把风险带到最后。
- **六个阶段没有可运行的窄验证点**：每阶段完成标准都很大，agent 会**提前宣布完成**；而真正的产品价值被埋在一大堆低价值边缘逻辑后面。

### 5.3 反直觉的观察
这种**穷举枚举、明确字段、明确 must/must-not** 的写法，正是 **AI 友好的规格风格**。若把它当**检索语料库**（"评论表的唯一约束是什么"→直接查），比给人看还有用。**问题是你不该把它当"线性施工脚本"。** 文档不是不好，是**用错了地方**。

## 6. 能不能落地

### 6.1 分维度评估

| 维度 | 能否落地 | 说明 |
|---|---|---|
| 单个功能（目录/评测/评论/登录…） | ✅ 能做 | 没有研究级难题，agent 能写 |
| 按规格"精确合规" | ❌ 基本不能 | 延迟循环外键、触发器盖楼、租约幂等队列、字节级续传、多源哈希一致——最难写最难测，最可能被悄悄简化或违反 |
| 关键路径的外部假设 | ❌ 未验证 | AI 审核、S3、GitHub 凭据全是"服务商以后填写"，但架构**依赖**它们按特定语义返回；接入前核心链路走的全是"故障/待处理"分支 |
| 核心技术栈 | ⚠️ 未验证 | 无 Linux/Docker 构建、无真实 OAuth；"证据"里 Node 版本都对不上；风险最高的集成被全推到第 6 阶段 |
| 正确性核心（状态机+并发） | ⚠️ 未验证 | 发布资格、晚到任务、撤回竞态、队列领取全靠时序正确，而现有测试不测时序 |
| 范围 vs 资源 | ❌ 明显超配 | 6 阶段 / 60+ 表 / 审核+整合包+批量导入+存储迁移+备份恢复+8 组后台+4 条端到端+13 类故障矩阵。即便 agent 包打字，**瓶颈也是审查与验证**，不是编码 |
| 长期可运维 | ❌ 单人不可持续 | 60+ 表 + 触发器 + 延迟外键 + 配置版本 + 审计，一个人记不住也改不动；备份/迁移/升级回退是**持续运营负担** |
| 双轨资产 | ❌ 治理风险 | 根目录文档说"尚未编码"，`符/` 里却已有整套工程和源码 zip；两个事实来源并存，人和 agent 都会踩坑 |

### 6.2 为什么"照原样"落不了地
1. **P0 = 整个产品**，又没有"全部完成"之前能上线的里程碑。于是"上线"等价于"几乎全做完"——最典型的**永远发不出去**的形态。
2. **规格 > 可验证能力**。文档用"必须验证…""不得…"覆盖海量不变量，但项目看不到匹配的测试/运维产能。结果就是**约束写在纸上、代码里走捷径**（关外键、JSON 塞结构化数据、跳过触发器）。
3. **关键风险全在最后**。最不确定的（真实 Linux、OAuth、审核、S3、恢复演练）安排在阶段 6；等发现不可行时，前面全是沉没成本。
4. **"已确认"变成了枷锁**。把每个决定都标成已确认，使"砍掉 70%"在心理和流程上都很困难（"可是第 106 节已经确认了"）。**规划的成熟度反而阻碍了它被修正。**

### 6.3 现实中最可能的结局
> 一个**能演示、浅层测试全绿、核心链路躲在"未接入/待处理/人工复核"分支后面**的系统。它**永远不会到达一个你敢宣布"上线"的状态**，且随表结构和状态机越铺越大，变成**你自己都不敢改**的代码库。
> 一句话：**demo-ready，production-not。**

## 7. 值得肯定的地方

- **对失败模式思考扎实**：同步失败保留上次成功资料、撤回/隐藏不被旧任务复活、历史快照不可变、"安装资料可获取 ≠ 实际安装成功"这类边界分得很清。
- **安全直觉好**：HttpOnly/Secure/SameSite + `__Host-` 前缀、state+PKCE、token 不进 Cookie、rehype-sanitize 且不执行 MDX、媒体访问绑定公开状态。
- **架构分层意识好**：模块化单体、外部服务走适配器接口、评论/审核/通知/配置抽公共能力、草稿用乐观并发版本号。
- **对"未验证"基本诚实**：没有 Docker、没有真实提供商接入，都作了标注。

问题不在想法不对，而在**把这些正确的原则一次性、全量、超前地实现到了一个无人使用、需求未验证的系统上**。

## 8. 改进建议

### 8.1 直接的第一步建议
不要问 agent "按这些文档实现这个项目"，改成：

> "读 `架构设计.md` §33–39 和 `数据库模型.md` 第 4/5 节作为参考，但只实现这条链路：GitHub 登录 → 收录一个插件 → 写/审/发一篇评测 → 评论。表控制在 20 张以内，先不建任务队列/多存储/批量导入。给出可运行的端到端测试，并说明哪些约束你**没有**实现。"

把范围钉死，把"没做什么"逼出来，比产出海量"已实现"更有价值。

### 8.2 让它能落地的条件
只有满足下面几条，才谈得上落地——而这几条本身就意味着**要推翻当前规划**：

1. **砍成一条垂直薄片并先上线**：登录 → 收录一个插件 → 写/审/发一篇评测 → 评论；表 ≤ 20 张。
2. **先验证 3 个最险的外部假设**：一条真实 GitHub 同步闭环、一次真实 OAuth 登录、一个真实 Linux 容器构建。过不了这三关，后面全是空中楼阁。
3. **重做版本证据**：在真实目标环境跑一遍，得到可用版本 + 锁文件。
4. **用无聊的成熟组件替换自研基础设施**：队列、存储、配置，别在 SQLite 上手搓。
5. **定义"远早于完成"的可发布里程碑**。
6. **单一事实来源**：文档与 `符/` 里的代码二选一，另一个归档。
7. **接受更简单的数据模型，让它长出来**，而不是一次定死 60 张表。

### 8.3 驱动 agent 施工的纪律
- **冻结一份"缩减版规格"**，不把整包规划丢给 agent。
- **提前替 agent 定掉所有有争议的技术选择**（队列、配置、上传、外键策略、缓存）；你不定，它就会自己发明一个错的。
- **把"验收测试"当作唯一契约**，要求可运行证据而非"已实现"。特别盯这几条反模式：是否偷偷 `PRAGMA foreign_keys=OFF` 或删外键；是否把规范化表换成 JSON blob 走捷径；触发器是否真的进了迁移；并发/幂等测试是否恒真。
- **按"垂直薄片"而非"六个大阶段"推进**：每个里程碑独立可运行、可测、可演示，完成即停，人工验收后再进入下一片；**绝不让它一次跑完六阶段**。
- **schema 与迁移人工过一遍**——这是唯一不能被"看起来对了"糊弄的地方。
- **先修版本证据**：重跑真实 Linux/容器环境验证，得到可用版本再写锁文件。
- 把设计文档降级为 **agent 的参考查询库**，不是施工顺序表。

## 9. 结语

判断力在及格线以上，但**克制力与优先级不合格**。它最擅长的恰恰是它最该少做的那件事——把不确定的世界写成确定的文档。

对这类附属站点来说，现在最缺的不是第 111 节设计，而是：**删掉前 110 节里 70% 的内容，然后写第一行代码。**
