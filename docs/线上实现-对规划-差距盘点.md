## 0. 一句话结论：**两把尺子，答案相反**

| 用哪把尺子量 | 线上实现的完成度 | 缺的是什么 |
|---|---|---|
| **尺子 A**：`idea.md` 的 P0 清单（已确认需求，472 行） | **约 1/5** | 缺一整个产品：整合包、通知、收藏/有帮助、举报与纠错、搜索、目录发现与每日同步、配置化、备份恢复、后台 7 组 |
| **尺子 B**：`架构设计.md` 的模块与数据实体（13 个业务模块 / 约 62 张业务表 + 3 张 FTS5 虚表） | **7/13 个模块、25/62 张表** | 同上，外加 packs / interactions / cases / search / notifications / settings 六个模块整体缺席 |
| **尺子 C**：`设计评审意见.md` 第 8 节的整改要求（**砍成一条垂直薄片、表 ≤20、先验 3 个最险外部假设**） | **基本达成，而且已经上线** | 评审当时预判的结局是"demo-ready, production-not"；现在确实"能跑、真机、但离 production 还差 HTTPS / 备份 / 加固" |

**所以"差距"这个问题必须先说清跟谁比。** 按尺子 A 说，这是个刚起了个头的大项目；
按尺子 C 说，这是照着评审意见把该做的先做了，并且比评审预期多走了一步（真上线了）。

> 评审原话：这不是过度设计，而是"把设计本身当成交付物"；并直接指出 **P0 名不副实、优先级是反的**，
> 要求"只实现 GitHub 登录→收录一个插件→写/审/发一篇评测→评论，表 ≤20，先不建任务队列/多存储/批量导入"。

**服务端**：9 个模块（identity / catalog / reviews / content / comments / moderation / media / tasks / operations）
+ 4 个 workflow（submit-review / publish-review / publish-comment / decide-submission）
+ worker 4 个处理器（review_check / review_publish / comment_check / comment_publish）

**数据库 25 张表**（迁移是权威结构）：账号身份 4、插件 2、内容与评测 6、评论 2、提交与任务 4、
媒体 5、操作/配置 3、草稿回执 1（含 `site_settings`、`configuration_revisions` 两张**有表无事**）

**线上部署**：Debian 13 VPS `http://5.231.26.36`，`dsh-review-web`（:80，只借 `CAP_NET_BIND_SERVICE`）
+ `dsh-review-worker` 双 systemd，跑在 `dsh` 用户下，SQLite WAL，已跑通真实 GitHub 登录。
