# 技术选型：基础功能该用库，还是自己写

> 2026-10-13 调查。方法：**声明 vs 实际引用逐文件核对**（`src/`、`tests/`、`scripts/` 全扫），
> 候选库只采信**官方 README / wiki / 官方文档**。所有结论都可以按 §5 的命令复核。
>
> 一句话结论：**本切片一个新库都不用引入；反而该删两个白声明的依赖、补一个该声明的。**

## 1. 一页结论

| 基础功能 | 现状 | 结论 |
|---|---|---|
| Markdown 渲染 + HTML 净化 | `unified` + `remark-parse/gfm/rehype` + `rehype-sanitize` | ✅ **用对了库**，继续 |

| 持久任务队列 + 租约 | 自研（CAS + 幂等键 + 到期回收，有专门测试） | 🖐️ 继续自研（换库收益为负） |

| 备份 | 无 | 🖐️ `better-sqlite3` 的 backup API，**不需要库** |
| 时区 / 日期 | `Intl`（内建） | 🖐️ 不需要库 |
| UUIDv7 / ID | 自研（crypto + 时间戳 + 格式锁） | 🖐️ 继续 |
| 前端请求封装 | 自研 `apiFetch`（薄信封） | 🖐️ 继续；不需要 axios / ky |
| 表单 | 手写受控组件 | 🖐️ 继续（字段少；引 `react-hook-form` 会把 `zod` 又拖回来） |

## 2. 三项已执行的动作

### 2.1 `sharp` 显式声明（原为隐患，已修）

- **事实**：`src/server/modules/media/service.ts:11` 直接 `import sharp from 'sharp'`；
  而 `sharp@0.35.5` 原先只是 `next` 的 `optionalDependencies`（`^0.35.4`）**顺带装上的**。
- **风险**：换 pnpm（严格 `node_modules`）会直接 `MODULE_NOT_FOUND`；`npm ci --omit=optional` 会让**图片上传炸掉**。
  同类问题在别的项目已被提成 issue（[FediHome #245](https://github.com/TemujinCalidius/FediHome/issues/245)），
  Next 官方也把"缺 sharp"列为生产错误（[install-sharp](https://nextjs.org/docs/messages/install-sharp)、
  [sharp-missing-in-production](https://nextjs.org/docs/messages/sharp-missing-in-production)）。
- **好消息**：Next 的默认外置清单 `node_modules/next/dist/lib/server-external-packages.jsonc`
  **同时包含 `sharp` 与 `better-sqlite3`** → 声明它不会被 Turbopack 尝试打包。
- **已做**：`dependencies` 加 `"sharp": "0.35.5"`（与已装版本精确对齐），并**实测构建通过**
  （见 §5；社区确有 [Turbopack + sharp 讨论](https://github.com/vercel/next.js/discussions/83230)，所以必须实测而不是推断）。
- **仍未做**：容器里的 **图片上传真跑一遍**（目前只验过页面与健康检查，没验过上传）。

### 2.2 频控已上 `rate-limiter-flexible`（已实施，迁移 0006）

- 规划要求（`参数与管理规则.md` 第 22-29 行）：评论变更 5 次/分/用户、指定插件提交检查 10 次/时/用户；
  超限给明确等待信息；**不能只靠前端放行**。
- 采用的库特点（[README v11](https://cdn.jsdelivr.net/npm/rate-limiter-flexible@11.0.0/README.md)、
  [SQLite wiki](https://raw.githubusercontent.com/wiki/animir/node-rate-limiter-flexible/SQLite.md)）：
  - **零生产依赖**、自带 TypeScript 类型；
  - **原子自增**：SQLite store 用**单条 `INSERT ... ON CONFLICT ... RETURNING`**（已核对其源码 11.2.2），
    并发下不会"两个请求都读到 4 再各写 5"；
  - **直接吃 `better-sqlite3`**（`storeType`），不必拖进 knex / redis；
  - 提供 `consume/get/reward/penalty` 与 `msBeforeNext` —— 后者正好用于"明确等待秒数"。
- **实际落地方式**（与最初的设想有一处不同，值得记下）：
  - 表**由我们自己的迁移 0006 建**（DDL 照抄库自建的那份），limiter 用 `tableCreated: true` 构造，
    **不让库运行时偷偷建表**（保持"权威结构是 migrations/*.sql"）；
  - 关掉库的 `clearExpiredByTimeout`：它会 `setInterval`，而我们要求进程能被干净关掉
    （键是"用户 × 动作"，与用户数同阶，不清理也不会涨爆）；
  - 落点是**路由层**（`POST /api/plugins`、`POST .../comments`），且**在昂贵动作之前**：
    插件收录会出网探测 GitHub，等业务层拒绝就已经替超限用户花掉了上游额度。
- **三条如实说明的偏差**（写在 `src/server/platform/rate-limit.ts` 注释里）：
  1. 窗口是"从该用户第一次操作开始计时"的**增强固定窗口**，不是严格滑动窗口（交界处最坏可到 2 倍）；
  2. 规则目前是**模块常量**，还没接 `site_settings`（规格要求"后台可调整"）；
  3. **被拒的请求也会把原始计数加上去**（库的语义），但窗口终点不被推后，所以刷不会延长封禁。

### 2.3 删掉两个"声明但零引用"的依赖（已做）

| 依赖 | 实情 | 处理 |
|---|---|---|
| `zod` | `src/`、`tests/`、`scripts/` **全仓 0 引用**；校验是共享契约里的手写谓词 + 数据库 `CHECK` | 已 `npm uninstall` |
| `drizzle-orm` | 同样 0 引用（`docs/最小切片-设计映射.md` 早已把它记为"已知未收口项"） | 已 `npm uninstall` |

## 3. 搜索专项（本切片唯一真要选型的点）

| 路线 | 中文契合度 | 能否与 SQL 分页/计数/筛选组合 | 运维成本 | 结论 |
|---|---|---|---|---|
| **SQL `LIKE`（无库）** | 子串匹配天然可用 | ✅ 同一个 `WHERE` 里组合 | 0 | **先用它** |
| **SQLite FTS5（内建，非第三方）** | ⚠️ 有坑：trigram 分词器对 CJK 会出现 `textScore=0`（[openclaw #92061](https://github.com/openclaw/openclaw/issues/92061)）；**少于 3 字的词**还需 [better-trigram](https://github.com/streetwriters/sqlite-better-trigram)；业界兜底是"字符 bigram"（[TencentDB-Agent-Memory #1408](https://github.com/TencentCloud/TencentDB-Agent-Memory/pull/1408)） | ✅ 仍是 SQL | 低（同一个库） | **单独一片**，先做打分实验 |
| **JS 内存库（MiniSearch 等）** | ⚠️ 默认按空格/标点分词 —— 中文整段会变成一个 token，**必须自定义 tokenizer**；`filter` 作用在**内存结果**上 | ❌ 与"真实总数 + 分页 + SQL 筛选"打架 | 低 | 不采用 |
| **外部引擎（Meilisearch / Typesense）** | ✅ 但要额外服务与同步 | ✅ | 高（多一个服务、凭据、同步链路） | 规模不到，不采用 |

依据：[MiniSearch README](https://cdn.jsdelivr.net/npm/minisearch/README.md) 里 `tokenize` / `processTerm` / `filter` 的实际语义。

> 本仓的 `LIKE` 实现有一条**必须遵守**的纪律：用户输入里的 `%`、`_`、`\` 必须用 `ESCAPE` 转义，
> 否则用户输一个 `%` 就等于"匹配全表"。这条要有专门测试。

## 6. 边界（不要读成"永远不该用"）

- 认证 / ORM / 表单 / 状态管理这几项"不引入"是**基于当前薄片规模**的取舍，不是原则：
  一旦出现第二个登录提供方、或表结构复杂到需要迁移工具生成，就该重新评估（Auth.js / Drizzle 那时才值得谈）。
- 版本会变：本文基于 `next 16.4.0` / `sharp 0.35.5` / `rate-limiter-flexible 11.x` 的**实际读取结果**。
  落地时若版本已变，以 §4 的实测结论为准，不要照抄本文的版本号。
- 本文只覆盖**基础功能的技术选型**，不含产品功能取舍（那部分见
  [线上实现-对规划-差距盘点.md](线上实现-对规划-差距盘点.md)）。
