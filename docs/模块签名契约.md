# 模块签名契约（并行统一接口）

所有业务模块**只导出服务对象**，不导出仓储与表定义。签名统一，避免并行时互相猜。

## 0. 调用上下文

```ts
// src/server/platform/context.ts（GF 提供）
export interface CallerContext {
  /** 站内用户 ID；匿名访问为 null。 */
  userId: string | null;
  /** 当前角色，每次请求从数据库读取，不缓存。 */
  role: 'user' | 'admin' | null;
  /** 当前账户状态。 */
  accountStatus: 'active' | 'disabled' | null;
}
```

模块方法一律接收 `ctx: CallerContext`，**不读 Cookie、不读 HTTP 对象**。

```ts
  listPlugins(req: PluginDirectoryQuery): Promise<PageResult<PluginSummary>>;

  listPluginTags(): Promise<PluginTagSummary[]>;

```

`PluginDirectoryQuery` = `PageRequest & { q?, tag?, hasReviews?: 'all'|'yes'|'no', sort?: 'info'|'reviews' }`。
`PluginSummary` / `PluginView` 在迁移 0005 后额外带 `displayName / description / topics / authorLogin /
manifestVersion / infoUpdatedAt / repoUpdatedAt / publicReviewCount`（详情视图不含计数）。

**目录计数与筛选的判据必须唯一**：`plugins` 的公开评测数、`has_reviews` 筛选、`sort=reviews`
三处共用同一段 SQL（`PUBLIC_REVIEW_COUNT_SQL`），且必须与 content 模块的
`resolveVisibilityInTx`（存在已发布修订 + 未撤回 + 未隐藏）**逐条一致**；
`tests/catalog-browse.test.ts` 用"撤回一篇评测"的用例锁住这条一致性。

收录检查（需求第 1 节）：仓库可访问 **且** 对应 `package.json` 有 `dsh.bundle` 声明 **且** 引用的配置文件存在。
重复按 `(repository_id, plugin_path)` 判定；已有条目只更新资料（含展示字段与 `info_updated_at`），不重复创建。

**频控（平台层 `src/server/platform/rate-limit.ts`，由路由调用）**：
`enforceRateLimit(db, action, userId)` 消耗额度；超限抛 `rate_limited`（HTTP 429，
`context` 带 `retry_after_seconds` / `limit` / `window_seconds`，供页面提示等待）。
**幂等重放必须退还额度**（规格：重放不另算一次提交）：评论看 `created === false`，
插件收录看 `replayed === true`，两条路径都用 `refundQuietly(ticket)` 退还 ——
退还失败只记日志，**不能盖住原始错误**。挂载点是路由且在昂贵动作之前
（插件收录会出网探测 GitHub，先限流再探测）。规则值见 `RATE_LIMIT_RULES`（迁移 0006 建表）。

## 2.1 自动发现（`modules/catalog/discovery.ts` + `adapters/catalog/github-discovery.ts`）

任务类型 `plugin_discovery`（迁移 0007 加入 `TaskTypes`）。职责边界刻意分成两层：

| 层 | 职责 | 失败语义 |
|---|---|---|
| **发现适配器** | 找候选仓库 → 读树找 `package.json` → 取 `dsh.bundle` → 给可收录 URL | 允许**重试退避**（后台任务，偶发断流不该让一天的活白跑）；403 按证据分派：配额耗尽→限流，其余→`target_unavailable`（候选级跳过） |
| **收录（catalog 服务）** | **权威判定**：仓库可访问 + 声明 `dsh.bundle` + 文件存在 | 单条失败不影响整轮；只有上游整体故障才整轮失败（交队列重试） |

```ts
createPluginDiscoveryService({ db, discovery, probe }).run({
  runKey: string;          // 审计/幂等前缀：定时 'daily:YYYY-MM-DD'，手动 'manual:<ISO>'
  taskId: string | null;   // 写进 operation_records.task_id（有外键，必须指向真实任务）
  query?, searchPages?, perPage?, maxCandidates?, maxPlugins?, maxRequests?;
}): Promise<DiscoveryRunSummary>   // { searchedRepos, truncated, truncatedReason, pluginsFound, accepted, created, refreshed, skipped[], requestsUsed }
```

`acceptPluginSubmissionBySystem({ url, operationKey, taskId }, { probe })`：与用户路径**共用**检查与入库，
审计记 `actor_kind='system'` + `actor_user_id=NULL` + `task_id`，**不做同键重放**，
**不占用户额度**（走系统调度预算），**无 HTTP 路由**。
`discoveryBudgetFor(env)` 按有没有 `GITHUB_TOKEN` 分档（未认证 58 次/轮 ↔ 认证 400 次/轮）。

**任务进度的落点**：`HandlerResult.progress` → `background_tasks.progress`（迁移 0001 就有这列，
此前从未被写过）。后台页与诊断据此显示"这一轮发现了什么"，不必翻日志。

## 7. tasks（GT 负责）

**导出形状（以实际实现为准，2026-10-11 主控裁决）**：

本模块**没有 `index.ts`**，从 `@/server/modules/tasks/service` 导入。
导出的是「**工厂 + 进程单例访问器**」，不是契约早期草案里写的"服务对象"：

```ts
export interface TasksService { /* 方法见下 */ }
export function createTasksService(db: SqliteDatabase): TasksService;  // 工厂：显式绑定连接
export function tasksService(): TasksService;                          // 进程单例访问器（注意是函数）
export function resetTasksService(): void;                             // 仅测试/维护
```

> **裁决理由**：工厂 + 单例是**更好**的形状 —— 它让调用方能显式传入**同一条连接**。
> 若只有单例，评论写入走注入连接、而任务入队走 `getDb()` 单例时，会写出指向别处数据库的任务，
> 「看着成功、实际对不上」。因此**以实际实现为准**，契约随实现更新（本节）。
> 调用方（如 comments）应按 `createTasksService(db)` 优先、单例兜底的方式适配，见 `modules/comments/index.ts`。

```ts
export interface tasksService {
  /** 入队（与业务提交同事务）；同 (task_type, deduplication_key) 复用既有任务。 */
  enqueue(input: {
    taskType: TaskType; deduplicationKey: string; requestedBy: string | null;
    payload: unknown; schedulingGroup: string; availableAt: number;
    tx?: unknown; // 由调用方传入事务句柄，见 platform/db
  }): Promise<{ taskId: string; created: boolean }>;
  /** 原子领取一个可执行任务。 */
  claim(workerReference: string, now: number): Promise<ClaimedTask | null>;
  /** 续期（校验 token + 未过期）。 */
  renew(claim: { taskId: string; executionToken: string }, now: number): Promise<boolean>;
  /** 结束（成功／可重试故障／终态失败）。 */
  finish(claim: { taskId: string; executionToken: string }, input: {
    outcome: 'success'|'error'|'skipped'; errorCode?: string; errorSummary?: string; now: number;
  }): Promise<void>;
  /** 到期恢复扫描：把过期 running 置为 lease_expired 并重新安排。 */
  recoverExpired(now: number): Promise<number>;
}
```

**已确认的装配边界（主控裁决）**：

- worker 的 **handlers 注册表当前为空**。真实处理器（`review_check` / `review_publish`）属于
  `workflows` 层，由主控（GX）装配。未注册的任务类型被记为 `skipped` + `no_handler`，
  **不会假装成功** —— 这是正确行为，保留。
- **内容筛查适配器 `contentScreen` 由装配方注入**；`moderationService()` 进程单例默认**不注入**（= 未配置）。
  未配置时按既定规则停在 `manual_review` 或回 `pending` 并记 `fault`，**绝不自动放行**。


参数（架构第 101、102、103 节）：`max_concurrent=4`、`lease=120s`、`renew=30s`、`recovery_scan=10s`、
普通可恢复故障最多 3 次、等待序列 `[30s, 120s]`、常规单次任务上限 `300s`。

## 9. 主控裁决记录（2026-10-11，GC 提出的 5 项）

这些是并行施工中真实出现的边界歧义，逐条定案，避免后续反复。

### 9.1 `createOrGetDraft` 不写 `draft_save_receipts` —— 确认正确，不改

- `draft_save_receipts` 有 `CHECK (result_version = expected_version + 1)`，其语义是**一次 save 的回执**。
- 「初建草稿」不是 save，没有 `expected_version` 可与之一致，写不出合法回执行。
- 当前语义足够：同 (作者, 插件) 复用同一草稿（由 `uq_drafts_review` 保证），故同 `requestKey` 重复调用结果一致。
- **定案**：不写回执。契约（本文档 §3）本就只对 `saveDraft` 要求回执。

### 9.2 评论入队在业务事务**之后** —— 接受现状，但遗留为已知偏离

- 契约 §5 原文写「同一事务建立评论、修订、提交、检查任务」。
- 现实约束：`withTransaction` 回调必须同步（better-sqlite3 事务是同步的），而 tasks 的动态 import 是异步的。
- GC 的当前行为：评论创建成功、入队失败则**向上抛错让调用方重试**，不静默吞掉。
- **定案**：本切片**接受**该偏离，并登记为「未按文档实现」的第 9.2 条。
  真正的修法是让 tasks 以**静态 import** 暴露同步 `enqueue`，属于后续收口，不在本切片范围。
- **为什么可以接受**：失败是显式可见的（抛错），不会出现"评论已建但没人检查"却显示成功的假象。

### 9.3 `hide` / `unhide` / `withdraw` 暂不接 `operation_records` 去重 —— 接受

- 这三个动作目前只做 `requestKey` 非空校验。`operation_records` 属 GT 桶，任务描述未要求接入。
- **定案**：本切片接受为已知缺口，登记进「未实现清单」（幂等性只覆盖草稿保存、提交、插件收录三处）。

### 9.4 服务方法末尾的连接注入口（`db?: SqliteDatabase`）—— 保留

- 用途：测试注入临时库。
- **定案**：保留。这是本切片"每个测试用真实临时库"的必要条件；接口层正常调用不传即可。
  若日后要完全隐藏，改为内部连接提供者即可，不影响调用方。

### 9.5 `listDrafts` 额外导出 —— 保留

- 非契约导出，供个人中心工作台使用。
- **定案**：保留（页面需要），但**不进契约**，属便利方法。

### 9.6 `withdraw(reason: null)` 的占位文案 —— 确认正确

- 表有 `CHECK ((withdrawn_at IS NULL) = (withdrawal_reason IS NULL))`：撤回时间与原因必须同生共死。
- 作者未填原因时直接写 `null` 会被 CHECK 拒绝，冒出**裸 SqliteError**（会被接口层折成 500）。
- GC 改为落一个明确的占位文案（`DEFAULT_WITHDRAWAL_REASON`），并补两条用例（占位文案 + 直接 SQL 只写时间必被拒）。
- **定案**：正确。既不丢事实，也不破坏成对约束。

### 9.7 `runRuleCheck` 两条分支无法做集成测试 —— 确认边界

- 「标题非空」与「插件未绑定」在库里表达不出：`review_revisions.title` 有 `CHECK(trim(title)<>'')`，
  `plugin_id` 是 NOT NULL 外键。
- GT 的做法：这两条只由 `evaluateRules` **纯函数**用例覆盖；集成层测「版本字段缺失」这条真能落库的缺项。
- **定案**：接受。**不允许**为了让集成测试覆盖而放宽表约束 —— 约束是防线的价值高于测试覆盖率数字。
  在「未实现清单」里如实登记该覆盖边界。
